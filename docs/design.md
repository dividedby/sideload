# sideload design

Revision 2 (Swift architecture), 2026-10-19; free-team signing added 2026-10-23 (section 18, design only). Supersedes the Node-era design. The Node implementation (`src/`, `bin/`, its tests) was deleted on 2026-10-20 after Swift reached parity (section 14). The secrets pre-commit hook (`scripts/check-secrets.mjs`, its test, a trimmed `package.json`) stays as dev tooling.

## 1. Goals and non-goals

**Goals**
- Sign and install apps on the owner's own devices with the paid team (7AGMPUPP64), using only Apple tools: `xcodebuild`, `codesign`, `security`, `xcrun devicectl`, plus Security.framework.
- Detect cheaply and repeatably whether Apple has fixed the 0xe8008018 install block (`canary`), without touching a real app.
- Audit the paid team's developer portal read-only (`portal`): certificates, App IDs, devices and profiles, through an App Store Connect API key the owner provides. Every request is a `GET`; no code path can change the portal.
- Export the dev cert (.p12) and profile for Feather's on-device re-signing; track expiry and warn at 60 and 14 days (paid; free installs use 3 and 1 days, section 18).
- One small arm64-only Swift package, zero third-party dependencies, three artifacts on one core: `SideloadCore` library, `sideload` CLI (one JSON object on stdout), `SideloadMenu` menu bar app.
- Built for the owner's paid Apple Developer account. The owner's free team (6ZU5Z6ZKK7) is supported only as the narrow, allowlisted interim route of section 18 (owner decision 2026-10-23, superseding the 2026-10-20 refusal of free teams); every other free or personal team is still refused. Sign-in is via Xcode's account; there is no in-app Apple ID login.
- Interim route while the paid block stands (design, not built, section 18): re-sign apps with the free team's existing pinned identity under `io.github.dividedby.free.*` and keep them alive with a guarded 7-day refresh.
- Light on an M1 Air with 8 GB: no polling loops, no resident helpers; refresh on demand or on a launchd schedule.

**Non-goals**
- No third-party sideloaders (iLoader, Sideloadly, AltServer, SideStore, Impactor, LocalDevVPN). Feather's on-device install route is not used: installs happen from the Mac via this tool; Feather only manages and re-signs on the phone.
- No Apple ID passwords; Xcode holds the account.
- Free team (6ZU5Z6ZKK7): narrow use only, per the AGENTS.md rule. Never create, revoke or export its certificate; never install, uninstall, re-sign or launch any bundle ID outside `io.github.dividedby.free.*`; never touch mobile-safari-lab or WebDriverAgent (atvloadly and its `atv` VM are retired, section 18). `canary`, `export-cert`, `portal` and the ledger's certificate/profile lists stay paid-only.
- No "whatever is connected" targeting. No pairing (`devicectl manage pair` is owner-only), no keychain or portal deletes, no root/elevated privileges, no system-wide installs without owner approval.
- No Swift package dependencies (no swift-argument-parser). System frameworks (Foundation, Security, CryptoKit, SwiftUI, UserNotifications) are not dependencies.

`Commands/*` are plain async functions: `(Services, Options) async -> CommandResult`. `Services` carries `runner`, `fs`, `clock`, `keychain`, `http`, `home`, `log`. The CLI and the app build the same `Services`; tests build fakes. Nothing in Core imports AppKit or SwiftUI.

**Toolchain.** Swift 6.4 is installed. Use Swift 6 language mode (strict concurrency complete) in every target. All shared types are `Sendable` value types; mutable shared state is limited to the live-children registry and the config store, each behind a lock. Release build: `swift build -c release --arch arm64`, `-Osize`, `-Xlinker -dead_strip` (both in `Package.swift`), then `strip` (a post-build step SPM can't express; `make-app.sh` runs it). `make-app.sh` and CI refuse non-arm64 hosts; the app's Info.plist sets `LSRequiresNativeExecution` so it never runs translated.

## 4. Producing the menu bar `.app`

SPM emits executables, not bundles. Two options:

| | Committed `.xcodeproj` | `scripts/make-app.sh` over an SPM executable |
|---|---|---|
| Build graph | Second graph beside Package.swift; Core must be consumed as a local package | One graph (SPM) |
| Maintenance | Hand-written pbxproj (the canary one already carries this risk on Xcode 27) | ~40 lines of shell |
| Signing control | Xcode may try to provision with the account | Explicit `codesign`, no account involvement |
| Review | pbxproj diffs are noisy | Plain script |

**Choice: build script.** It keeps SPM the single source of truth, avoids a second pbxproj, and cannot trigger portal access.

`make-app.sh` steps: refuse non-arm64; `swift build -c release --arch arm64 --product SideloadMenu`; create `.build/app/SideloadMenu.app/Contents/{MacOS,Resources}`; copy the binary; write `Info.plist` (below); copy `canary/Canary.xcodeproj` and `canary/Canary/` (the project and its sources, nothing else from `canary/`) into `Contents/Resources/canary/` so the app's canary action has the payload; `codesign --force --sign - --options runtime --timestamp=none <app>`; `codesign --verify --strict`. The app finds the project at `Bundle.main.resourceURL/canary/Canary.xcodeproj` and passes it as `Services.canaryProject`; the CLI, with no bundle, falls back to the repo's `canary/Canary.xcodeproj` located from the Swift source file (`CanaryCommand.defaultProject`). The canary build writes derived data to `$SIDELOAD_HOME/builds/canary`, never into the bundle, so the signed seal stays intact. Output stays under `.build/` (gitignored); the owner copies it to `~/Applications` (user-level, not system-wide).

Info.plist keys: `CFBundleIdentifier io.github.dividedby.sideload.menu`, `CFBundleName`, `CFBundleExecutable`, `CFBundleShortVersionString`, `LSMinimumSystemVersion`, `LSUIElement true` (menu bar only, no Dock icon, no app switcher entry), `LSRequiresNativeExecution true`, `NSHumanReadableCopyright`.

**Local signing.** Ad-hoc (`codesign -s -`) is sufficient: the app is built on the Mac that runs it, carries no quarantine attribute, so Gatekeeper does not block it. It needs no certificate, no Apple ID, no profile, and does not touch the developer portal or the free team's cert. No sandbox, no special entitlements. Consequence: an ad-hoc identity is the code hash, so each rebuild is a "new" app to the keychain (section 6).

## 5. Process runner

Invariants carried over from the former Node runner. Foundation `Process` cannot put a child in its own process group (no API), and the group kill is what stops `xcodebuild` helpers. **Use `posix_spawn`** with `POSIX_SPAWN_SETPGROUP` (group 0), `posix_spawn_file_actions` for pipes and stdin.

```
protocol Runner: Sendable {
  func run(_ spec: CommandSpec) async -> RunResult      // never throws for non-zero exit
}
CommandSpec { executable: String, args: [String], timeout: Duration (required, > 0),
              stdin: Data?, cwd: String?, maxOutputBytes: Int (default 32 MiB) }
RunResult   { code: Int32?, signal: Int32?, stdout: String, stderr: String,
              timedOut: Bool, overflow: Bool, spawnError: String? }
```

Invariants (each gets a test):
- Argument array only; no shell. `CommandSpec` init traps on empty executable or non-positive timeout (the `assertRunArgs` equivalent).
- Mandatory timeout: no default, no "infinite".
- One thread per run does a blocking `poll(2)` over stdout, stderr, stdin-writable, and a wake pipe until the deadline. This is event-driven (no sleep loop), writes stdin without deadlock, and enforces `maxOutputBytes` across stdout+stderr combined; on overflow it stops reading and escalates.
- Escalation: `killpg(SIGTERM)`, 2 s grace, `killpg(SIGKILL)`; a final group SIGKILL after reaping when the run timed out, overflowed or was cancelled, so nothing is orphaned. `waitpid(WNOHANG)` reaps; after the final SIGKILL it is polled for at most 5 s, then the run returns with `code` and `signal` nil (status unknown, child left unreaped) so a child stuck in an uninterruptible state cannot defeat the timeout.
- stdin is always closed after writing `input` (empty if none) so tools never block on it.
- Spawn failure returns `spawnError: "ENOENT"` etc., not a throw.
- Task cancellation writes the wake pipe; the loop escalates immediately (this is how the app's Cancel button works).
- A lock-protected `LiveChildren` set holds child pgids. The CLI installs `DispatchSource` handlers for SIGINT/SIGTERM/SIGHUP that `killpg(SIGKILL)` every live group, emit one `INTERRUPTED` object (if none emitted), and exit 128+signo. `Interrupt` is the single owner of stdout and of the process exit: one `Mutex` state (`stdout: idle | writing(main|handler) | done`, the recorded signal, `exiting`) decides who writes and who exits, held only for O(1) transitions and never across a write, `killAll`, sleep or wait. The main flow calls `finishMain(envelope)`: it renders, yields without writing if a signal was already recorded, otherwise writes and returns `.exit(code)`, `.writeFailed` (exit 70) or `.yield` (a signal arrived during the write; main parks, since falling off the end of `main.swift` would `exit(0)`). The handler records the signal first, then kills the groups (spawns in flight are waited for up to 500 ms), then writes `INTERRUPTED` on its own thread if stdout was idle, or waits if main is mid-write, in both cases for at most 1 s so a full pipe cannot hold the process, and returns 128+signo for the caller to `_exit` (not `exit`, so stdio flush cannot block after an abandoned write). Later signals, and signals after main committed to exiting, park. An object is complete only if its write finishes within that second: pipe writes up to PIPE_BUF are atomic, longer ones can be cut if the reader stalls. Residual risk: a `posix_spawn` that takes longer than the 500 ms wait can orphan its child at exit. `SIGPIPE` is ignored; a closed stdout is not a failure.
- Environment is inherited unchanged; nothing secret is ever placed in argv (see section 6).

`DeviceCtl` wraps the runner: resolves an alias to the saved CoreDevice UUID (fallback UDID); rejects any `--device` value (including `-d=<value>`, which is also stripped and validated; stricter than Node) that is not a saved ID; rejects caller-supplied `--timeout`/`--json-output`; rejects positionals starting with `-`; always passes `--timeout` and `--json-output <random path in the 0700 tmp/>` (devicectl writes the file; it is not pre-created), runs `xcrun devicectl ...` with timeout `timeoutSec + 15`, chmods the file 0600, parses the JSON file only, deletes it on every path, and surfaces overflow as `OUTPUT_LIMIT`.

## 6. Keychain: Security.framework in-process

**Choice: Security.framework**, behind protocols with fakes in tests: `KeychainClient` (read-only public-certificate reads), `IdentityExporter` (private-key export), `SecretStore` (the password item) and `P12Verifier` (open an exported file). The last three have inert `Services` defaults that throw `KeychainFailure.unavailable` (`KEYCHAIN_UNAVAILABLE`), so a test that forgets a fake never reaches the real keychain; every failure is a `KeychainFailure` whose `report` is the `{code, message, fix}` of the output contract. Reasons:
1. The p12 password never appears in argv. `security export` (password via its `-P` flag) and `security add-generic-password` (via `-w`) both put it in `ps`; the framework calls (`SecItemExport` with a passphrase parameter, `SecItemAdd`/`SecItemCopyMatching`) do not.
2. No text parsing: the Node path chains `find-identity`, `find-certificate -p`, and `openssl x509`. The framework returns `SecIdentity`/`SecCertificate` directly, removing two subprocess hops and `openssl`.
3. The app and CLI call it in-process; no shelling out.

Operations: list `kSecClassIdentity` for "Apple Development" (reference only; reading refs does not touch private keys, so it does not prompt while the login keychain is unlocked; whether a locked login keychain shows an unlock dialog is unverified, since the legacy keychain may ignore `LAContext.interactionNotAllowed`, and must be settled before `status` runs from launchd, see section 16); read subject OU and `notAfter` per certificate (team match is on OU, never name; the paid-only paths reject the free OU 6ZU5Z6ZKK7 as `FREE_TEAM_SELECTED`, and the free path accepts only the one pinned free identity, section 18); export the chosen identity as PKCS#12 with a generated password; store/read the password as a generic-password item (`service io.github.dividedby.sideload`, `account p12`).

**Valid identities only.** Node's `find-identity -v -p codesigning` hides expired, untrusted and revoked identities, so Swift does the same: `CodeSigningTrust` runs a synchronous `SecTrust` evaluation with the Apple code-signing policy (`SecPolicyCreateWithProperties(kSecPolicyAppleCodeSigning, nil)`), network fetch disabled, and `KeychainCertificate.isValidForCodeSigning` carries the result; `CertCheck` also drops certificates whose `notAfter` is past. Revocation status therefore relies on the local cache and may lag `find-identity -v`.

**Trade-offs accepted.**
- ACLs follow the caller's code identity. An ad-hoc rebuild changes the identity, so the owner sees a keychain prompt for the password item and private-key export after a rebuild, and the CLI and app are separate identities. This is acceptable: export and password reads are rare and owner-approved by design. The public-certificate reads used by `doctor` and `status` do not prompt.
- `security cms -D -i` (provisioning profile decode) stays a subprocess: it is Apple's tool, output is a plist, and the guard fixtures already pin it.
- Cert field extraction uses `SecCertificateCopyValues`. **Spike result (step 5, macOS 27 SDK):** it is available (10.7+), not deprecated, and returns subject OU (`2.5.4.11`, one entry per OU, in order), common name, and `notAfter` (a CFAbsoluteTime number), identical to the `openssl-paid`/`openssl-free` fixture outcomes on equivalent throwaway certificates (including GeneralizedTime dates). No DER fallback and no `openssl` were needed; `Keychain/CertificateReader` uses it directly.
- **Key export spike (2026-10-20, macOS 27 SDK, owner-approved, throwaway keychain only).** Run in one process against a fresh keychain file in a new temp directory (throwaway password, throwaway self-signed RSA-2048 identity imported with `SecPKCS12Import` into that keychain only); the login keychain and every other keychain were only counted (identities), never read by name, exported or written; the user search list was recorded first, was unchanged by the run, and was identical at the end; the temp keychain and directory were deleted (also on failure).
  - `SecItemExport(identity, .formatPKCS12, [], &params, &data)` with the passphrase as a `CFString` in `SecItemImportExportKeyParameters.passphrase` works in process, returns `errSecSuccess` in 0.01 s, with no argv. It is **not deprecated** (no warning); `SecKeychainCreate`/`Delete`/`Unlock`/`GetStatus` are deprecated and are used by tests only, inside a deprecated-attributed helper.
  - **PBE written: legacy.** The DER holds `pbeWithSHAAnd3-KeyTripleDES-CBC` (1.2.840.113549.1.12.1.3, the key bag) and `pbeWithSHAAnd40BitRC2-CBC` (1.2.840.113549.1.12.1.6, the certificate bag), MAC SHA-1; no PBES2/PBKDF2/AES. A p12 from this call needs OpenSSL 3's legacy provider to open. `Pkcs12Inspector` records it and `export-cert` will warn (`P12_LEGACY_ENCRYPTION`); whether Feather reads it is still unverified.
  - **`SecPKCS12Import` with `kSecImportToMemoryOnly` leaves nothing behind.** With a keychain also offered (`kSecImportExportKeychain`, which would receive the items if memory-only were ignored) the temp keychain's identity, key and certificate counts stayed 1/1/1 and the default search list's identity count stayed 2 (before, during, after). The production `P12Verifier` passes memory-only and no keychain; that exact call was not run against the default keychain, only inferred from the offered-keychain run. A wrong passphrase returns `errSecAuthFailed` (-25293), which `KeychainFailure.fromImport(status:)` maps to `.wrongPassword` (`P12_VERIFY_FAILED`; Deny/Cancel stay `.denied`); the file is still an identity-bearing PKCS#12 on success (`identity`, `chain`, `trust` keys).
  - **Dialogs.** The first run showed the owner a dialog "spike wants to use the keychain" asking for the new keychain's password. Cause: the spike called `SecKeychainSetSettings` (to disable auto-lock) on the keychain it had just created; writing a keychain's settings re-authenticates against its password (the keychain was already unlocked: `SecKeychainGetStatus` reported unlocked, readable, writable straight after `SecKeychainCreate`). With that call removed and the keychain unlocked in process with its throwaway password, the second run (create, unlock, import, find, export, memory-only import, delete) showed no dialog, and the export did not prompt for a key in a non-login keychain created by the same process (the importing process is in the key's ACL). Whether a key in the login keychain prompts is not something the spike could answer and is the owner's first real run. `PromptGuard` stays as the guard either way; Deny/Cancel maps to `KeychainFailure.denied`.
  - **`export-cert` flow (section 8).** Cheap checks first (usage, saved device, `--yes`, operation lock, ledger parse, public certificate and profile read, planner, `--out` validation, profile file read, master name free), then the password (read the item or generate and add it, so a `.p12` can never exist without a recoverable password; an empty stored value is `PASSWORD_UNREADABLE`), then the one private-key export, then verification (the file opens with the password and holds the planned certificate, else `P12_VERIFY_FAILED`), the master write, the staged kit (hidden temporary folder beside the destination), the ledger update (which also merges the certificates and profiles just read), and last the `renamex_np(RENAME_EXCL)` that puts the kit in place. A failure after the export removes the master and the staged kit; a failed rename also takes the export back out of the ledger. The three keychain calls that may raise a dialog (read item, add item, key export) run under `PromptGuard`.
  - **Password delivery: clipboard (owner decision 2026-10-20).** There is no `--show-password`. `--copy-password` writes one pasteboard item with the string plus empty `org.nspasteboard.ConcealedType` and `org.nspasteboard.TransientType` entries, records the change count its own write produced, logs "paste it into Feather now" to stderr, waits 90 s (`Services.sleep`, bounded and cancellable), and clears the pasteboard only if the change count is still that one. `NSPasteboard` is outside `SideloadCore`: Core defines `SecretPasteboard` (`copy`, `clearIfOurs`) and `PasteboardBackend` (`changeCount`, `replaceWithConcealed`, `clear`); `ConcealedClipboard` holds the "still ours" rule over any backend and is tested with a fake; the CLI's `AppKitPasteboardBackend` is the only AppKit code. `Services.pasteboard` defaults to an inert implementation (`PASTEBOARD_UNAVAILABLE`). `pbcopy` is not used: it cannot mark the item concealed. The first interrupt during the wait only ends it (`HoldSignal`; see "Clipboard exposure" in section 16) and the main flow clears and reports; otherwise the interrupt handlers in the CLI call `clearIfOurs` (bounded to 500 ms, a no-op until something was copied) before the process exits. The operation lock is released before the wait. If the kit cannot be moved into place and the ledger entry cannot be taken back out, the error is `LEDGER_ROLLBACK_FAILED` (the dangling entry is named; the owner removes it). Chosen over printing: a password in the terminal scroll-back or a log is permanent; on the clipboard it is short-lived and invisible to well-behaved managers. A safer variant, not built, would be a menu bar "Copy .p12 password" action that does the same copy without a 90 s CLI process.
  - **Not run:** `SecItemAdd`/`SecItemCopyMatching` of the `p12` password item against a real keychain (the opt-in `SIDELOAD_REAL_KEYCHAIN=1` test covers it, on a throwaway keychain only, and may show a dialog; it was not run in this PR), and Feather's reading of the p12.

## 7. Output contract and redaction

`Envelope` encodes `{ok, command, <data keys>, errors:[{code,message,fix}]}`; the envelope's own keys win over same-named data keys (Node let data override them). Data is a `JSONValue` enum (`null|bool|number|string|array|object`, Codable); typed command results are `Encodable` and converted to `JSONValue` before redaction. `JSONEncoder` with `.sortedKeys` and `.withoutEscapingSlashes` (deterministic key order is a deliberate difference from Node insertion order; consumers parse JSON, tests compare decoded values). Exit 0 iff `ok`, with one exception kept from the former Node CLI (its signal test asserted 143 after an `ok:true` emit): a signal that arrives while main is still inside its write makes the process exit 128+signo with that `ok:true` object on stdout. Main marks the write done and commits to exiting in one critical section, so once it has committed the signal parks and the process exits with main's own code. Progress goes to stderr and `logs/commands.log`, always redacted.

`Redactor` walks the `JSONValue` tree once, strings and object keys, last step before encoding: identity names → `Apple Development (identity hidden)`; modern UDID (8-16 hex), CoreDevice UUID, and legacy 40-hex IDs → `…ab12` (last 4, with the same boundary lookarounds); emails → `<email>`; a JWT → `<jwt>` and a PEM private-key block (an unterminated one to the end of the text) → `<private key>`, so the portal's bearer token and API key can never reach stdout or `commands.log`; `/Users/<name>` → `/Users/<user>`; caller-supplied literals masked. Regexes are compiled once as `NSRegularExpression` (Swift `Regex` rejects the lookbehinds these patterns need); `OutputTests` pin these cases. **Evidence bundles** (`canary --evidence`) do not use the `Redactor` or any masking. They are an allowlist built from structure (`EvidenceReduce.swift`, `EvidenceVocabulary.swift`, `EvidenceVerifier.swift`): every value is generated by sideload, or an Apple string admitted whole, or left out and counted; nothing is ever rewritten, so nothing is over-masked (a device called `Den` does not touch the word `identity`; the team ID stays). `ErrorChain.reduce` walks the devicectl `error` from the top (a node is an object with a string `domain` and an integer `code`; children are `userInfo.NSUnderlyingError` and each `NSMultipleUnderlyingErrorsKey`, pre-order; depth at most 8, 16 nodes; a node past those limits, or an error object without a string domain and an exact integer code, counts once in `omitted.nodes` and its children are not walked) and keeps per node only: `domain` (one of four known Apple domains, kept exactly with no subject check, since a short subject word such as `ice` can sit inside `com.apple.dt.CoreDeviceError`: that one, `com.apple.dt.MobileDeviceErrorDomain`, `IXUserPresentableErrorDomain` and `MIInstallerErrorDomain`; any other domain only if it matches `^[A-Za-z][A-Za-z0-9]*(\.[A-Za-z0-9]+)*$`, at most 96 characters, and holds no subject word; the verifier has its own copy of the list), `code` (an integer a double holds exactly, below 2^53; otherwise no node) and `codeHex` (32-bit two's complement, only when the code fits 32 bits signed or unsigned, else null), the three `NSLocalized*` texts, `LegacyErrorString` (one alphanumeric word), `LibMISErrorNumber` (an integer a double holds exactly, below 2^53, written as a decimal string; a larger value, as in the real capture, is left out and counted rather than written with invented digits, and `codeSignature.code` carries the status), and `info.outcome` (only `failed`, `success` or `succeeded`). Every other key (`NSURL`, `FunctionName`, `SourceFileLine`, paths) is ignored. A description of the form `Failed to verify code signature of <path> : 0x........ (<text>)` is taken apart: `codeSignature {code, message, appBundle}` with `appBundle` set only when the path ends in exactly `Canary.app`; the path is never kept. `MessageFilter.admit` accepts a text only if, after NFKC, straightened apostrophes and collapsed whitespace, it is at most 512 characters of `[A-Za-z0-9 .,;:()'-]` (plus the quotes around exactly `Canary` or the bundle ID, which counts as one token), every word is in the fixed vocabulary (Apple's install-error template words and sideload's own reason strings), every number is `0x` plus up to 8 hex digits or at most 10 decimal digits (the Apple case number is the one exception), and no subject word appears. Subject words (`SubjectTokens.make`) are the device names and hostnames split on `-._ `, the login, the full name's words, the person in each signing identity's common name (never its personal ID), this Mac's `ComputerName` and `LocalHostName` (looked up through `Services.machineNames` only when a canary run needs them), and the home folder's name, each folded (NFKD, marks stripped, lowercase, ASCII letters and digits) with a copy minus a trailing `s`, minus hardware words (`iphone`, `mac`, `pro`, ...). Domain, `LegacyErrorString` and outcome have no vocabulary, so for them every token of any length matches anywhere in the folded text (and a hex-run ID shape is refused). For messages, tokens of four or more characters match anywhere in the text's letters and digits run together; shorter ones only as whole words; the device IDs match with or without hyphens. Stderr lines go through the same filter (20 unique kept, the rest counted; a line with no letter or digit, such as a separator rule, is dropped without being counted). The verifier is independent: it receives the subject words as plain strings and has its own matching. It checks the closed schema (`EvidenceSchema.fields`: every path has a shape, an unknown key fails), the free-text paths (printable ASCII without `%+@/\_<>#=&?`, no subject word by the same four-or-more / whole-word rule), and both rendered files (no `@`, no `/users` in any case, no hex run of nine or more characters mixing letters and digits, neither device ID with hyphens removed). A hit writes nothing and returns the warning `EVIDENCE_REDACTION_FAILED` (the match itself is never repeated). Files go to a hidden temporary folder inside `evidence/` and the folder is renamed into place without overwriting. The certificate is identified by the first 8 hex digits of its SHA-1 only, never the serial or the full fingerprint, and never the common name. `logs/canary-install-*.json` is a different thing: a local log that keeps the raw devicectl document shape, masked by the old denylist (`InstallLogScrubber`: names, hostnames, this Mac's names, IDs, the person and the signing identities, case, apostrophe and hostname variants). It is never attached, the bundle never reads it, and its masking is best effort. Known limit of the bundle: a vocabulary miss omits a real Apple message (counted; the codes survive), so widen `EvidenceVocabulary` from future captures.

**Portal output is an allowlist.** `portal` projects each API resource onto fixed fields and never reads a name, display name, serial number, common name or profile content (the request's `fields[...]` parameter does not ask for them either). UDIDs print as the last four characters; certificates as the first 8 hex of their SHA-1; App ID identifiers only under `bundleIdPrefix` (otherwise `<other>` and a component count, unless the owner passes `--show-identifiers`, which still never prints an App ID name); portal ids of certificates, App IDs and profiles print in full because they are needed to act in the portal.

Exactly one stdout write per process; a second emit is a programmer error (precondition). `SideloadError(code, message, fix, data)` maps to `errors[]`; unknown errors become `INTERNAL_ERROR`.

`ArgParser` is a ~100-line hand-written parser: per-command option schema, `--opt value`, `--opt=value`, boolean flags, `-h`, unknown option or extra positional → `USAGE` JSON.

**`inspect`** (owner decisions 2026-10-22: Apple tools through the Runner, no in-process Mach-O or inflate code; no portal comparison in v1, so no flag; an unsafe archive is a hard failure). The IPA is untrusted input and is checked in three steps, each failing with one error and no output beyond it:
1. **Listing, before `ditto` runs.** This rejects known-bad archives; it is not the guarantee, because `ditto` extracts by the local headers and can write entries the central directory did not list (risk (a), section 16). Step 3 is the guarantee. The file is opened with `O_NOFOLLOW` (a symlink is `IPA_NOT_FOUND`), must be regular and at most 2 GiB. `ZipListing` reads only the central directory (bounded to 16 MiB, found by an end-record whose comment reaches exactly the end of the file; ZIP64, multi-disk and encrypted entries are `IPA_UNSUPPORTED_ZIP`, anything malformed `IPA_NOT_ZIP`) and refuses with `IPA_UNSAFE_ENTRY` an empty name, a NUL, backslash or control character, a leading `/`, a `..` component, a symlink, or a device, FIFO or socket (checked on the raw name bytes and, whatever the host byte says, the file-type bits in the high 16 bits of the external attributes, since `ditto` honours them for any host). More than 20,000 entries is `IPA_TOO_MANY_ENTRIES`; declared uncompressed sizes over 2 GiB per entry or 4 GiB in total are `IPA_TOO_LARGE`. Errors name the entry by index, never by name. Then the SHA-256 is streamed (CryptoKit).
2. **Extraction into a private folder.** `mkdtemp` makes `$SIDELOAD_HOME/tmp/inspect-XXXXXX` (0700) and `ditto -x -k --norsrc --noextattr --noqtn --noacl <ipa> <dir>/x` unpacks it (absolute path, argument array, 180 s timeout, 64 KiB output cap). Because a header can lie about sizes, a second task measures the folder every 250 ms and cancels `ditto` (the Runner escalates SIGTERM then SIGKILL on the group) when it passes 4 GiB or 40,000 entries: `IPA_TOO_LARGE`. Afterwards the path must still name the file that was listed and hashed (device, inode, size, mtime), else `IPA_CHANGED`.
3. **Walk before reading.** `ExtractedTree.verify` walks the folder with `lstat` only, never following a link: a symlink, a device, FIFO or socket, a hard-linked file, a different volume, nesting deeper than 40, more than 40,000 entries or 4 GiB of files is `IPA_UNSAFE_TREE` / `IPA_TOO_MANY_ENTRIES` / `IPA_TOO_LARGE`. Only then is anything opened. The archive must hold exactly one `Payload/*.app` (`IPA_NO_APP`, `IPA_MULTIPLE_APPS`).

Reading. `Info.plist` (and each `PlugIns/*.appex`'s) is opened `O_NOFOLLOW`, must be a regular file of at most 4 MiB, and is parsed with `PropertyListSerialization` (`INFO_PLIST_MISSING`, `INFO_PLIST_TOO_LARGE`, `INFO_PLIST_INVALID`; the parser's own error text, which can quote the document, is dropped). `CFBundleIdentifier` is required, and `CFBundleExecutable` must be a plain name: no `/`, NUL or control character, not `.` or `..`, at most 255 bytes, and a regular file inside the bundle (`IPA_EXECUTABLE_INVALID`). Architectures come from `lipo -archs` (a file that is not Mach-O is `IPA_NOT_MACHO`), platform and minimum OS from `vtool -show-build` (first slice; `LC_BUILD_VERSION` and the older `LC_VERSION_MIN_*`), falling back to the plist with the warning `BUILD_VERSION_UNREADABLE`, and entitlements from `codesign -d --entitlements - --xml <bundle>`. An unsigned bundle (`code object is not signed at all`) reports `signed: false`, `entitlements: null`, `appGroups: []`; a signed one with no entitlements blob has `{}`; any other `codesign` failure is `signed: null` with the warning `CODESIGN_FAILED`. Entitlements are copied into a bounded tree (depth 8, 4,000 nodes, 256 elements per array or object; strings and keys cut to 256 characters, data and dates replaced by a placeholder); every string taken from the archive is cut to 256 characters. `minOS` is the Mach-O value because that is what the OS enforces. `otherCode` counts `Frameworks/*.framework`, every `*.dylib` in the tree and `Watch/*.app`; `hasEmbeddedProvision` only tests that `embedded.mobileprovision` exists, the profile is never read. Tool output is parsed, never echoed: a failed tool is `TOOL_FAILED` or a warning naming the tool, with no stdout or stderr in it. Every Runner call has a timeout (30 s per tool) and an output cap (1 MiB).

Cleanup. The scratch folder is removed after every run, success or failure, by a removal that makes unreadable directories readable first (an archive can carry mode 000) and never follows a symlink; a folder that cannot be removed is the warning `SCRATCH_NOT_REMOVED`. The folder is also registered in `ScratchRegistry.shared`, and on every signal the CLI's handler kills the live child groups, removes any registered folders (bounded to 1 s; a no-op when none are registered) and closes the registry before the `INTERRUPTED` object is written; a command that starts after that gets `CANCELLED`. The signal tests run the built binary against a registered folder with an unreadable directory. SIGKILL or a crash can still leave an `inspect-*` folder in `tmp/`; delete it by hand. `fetch` calls the same `IPAInspector` on every download (the PlugIns list the Stremio source needs) (section 8, approved sources), so one unsafe-archive policy serves both.

**`export-cert` selection** (`ExportPlanner`, pure). Certificate: a valid, unexpired Apple Development certificate whose first OU is the paid team and whose subject carries no deny-listed OU. Profile: team `7AGMPUPP64`, unexpired, development (`get-task-allow` true and a non-empty `ProvisionedDevices`), platform iOS, listing the saved device's UDID (compared lowercase) and embedding the certificate; `--profile <uuid>` restricts the pool to that profile. Rank: a wildcard (`TEAM.*`) profile first, then the later certificate expiry, then the later profile expiry, then the UUID and certificate reference (deterministic). No candidate gives `CERT_NOT_FOUND`, `PROFILE_NOT_FOUND`, `DEVICE_NOT_IN_PROFILE` or `PROFILE_CERT_MISMATCH` in that order of how far the match got. An explicit-only profile still exports, with the warning `PROFILE_NOT_WILDCARD` (zsign picks a profile by bundle-ID suffix). tvOS is out of scope. `--out` must be absent or an empty folder and outside any repository (`OUT_NOT_EMPTY`, `OUT_IN_GIT_WORKTREE`); the default is `exports/feather-<UTC timestamp>`. The export is recorded in the ledger with the 8-hex certificate fingerprint, the profile UUID, the `.p12` master's home-relative name and first 8 hex of its SHA-256, the encryption label (`pkcs12-3des+pkcs12-rc2-40` on this Mac) and `passwordItem: keychain`.

**Approved sources** (`approvedSources` in config.json; `fetch` accepts nothing else):

**`fetch` flow (built, free-team step 4).** `approvedSources` entries are the owner's per-source switch: `{"app": "apollo"}`, `{"app": "stremio-ios"}`, `{"app": "stremio-tvos"}`, each optionally with a `hosts` list that can only narrow the catalog's allowlist (`SOURCE_NOT_ALLOWED` for an app that is unknown or not listed). The catalog is code (`FetchCatalog`) and pins the metadata URL, the asset selection and the hosts: metadata `api.github.com` (Apollo) or `raw.githubusercontent.com` (Stremio); download `github.com`, `objects.githubusercontent.com` and `release-assets.githubusercontent.com` (Apollo; the release asset URL on github.com redirects to the object store) or `dl.strem.io` alone (Stremio). Order: usage, source approved, stale `tmp/fetch-*` and `tmp/staged-*` swept (no lock; see "Locking" below), metadata GET, resolve, URL check (https, allowlisted host), then the manifest check: the same app and version already stored with the same upstream digest and an intact file downloads nothing (and removes a `tmp/staged-<digest>.ipa` an earlier busy run left for that digest); a different upstream digest for a stored version is `VERSION_CONTENT_CHANGED` (a swapped file) and nothing changes. Download (no `.op.lock`): `Services.http.download` streams (a `URLSessionDataDelegate` feeds a `DownloadFlow`; the sink gets 64 KiB pieces, whole blocks sliced rather than copied) to `tmp/fetch-XXXXXX/download.part` (0600) inside a `ScratchDirectory` (mkdtemp, 0700, registered in `ScratchRegistry` like an `inspect` folder, removed on every path; the CLI's signal handler removes it before exiting) next to a `live.lock` the run holds an `flock` on until the folder is gone; the digest is an incremental SHA-256 over the stream, capped at the size the source declares (and 2 GiB, `FetchLimits.maxIPABytes`, which `inspect` shares), `FetchLimits.maxRedirects` (3) redirects at most, 900 s overall, 30 s idle; the response's final URL is checked again. Then the byte count must equal the declared size (`SIZE_MISMATCH`, file deleted; a short body fails as a long one does) and our SHA-256 must equal the publisher's (`DIGEST_MISMATCH`, file deleted), the file is inspected with `IPAInspector` (an unsafe archive is the inspect error, file deleted, nothing recorded). Only then does `fetch` take `.op.lock` (the commit, synchronous, no awaits): it reloads `manifest.json` (another fetch may have written it meanwhile), re-checks the version (a different upstream digest is `VERSION_CONTENT_CHANGED` and the file is discarded; the same digest with an intact stored file means another fetch won, so ours is discarded and the result is `downloaded:false` with that entry's approval), renames the file into `downloads/<app>/<version>/<file>` (dirs 0700) and records it in `manifest.json` (0600, atomic write), then releases the lock. A busy lock at that point is `OPERATION_IN_PROGRESS` (never waited on), but the verified file is kept as `tmp/staged-<sha256>.ipa` (0600) for 24 hours and the fix says so; the re-run, after its metadata and URL checks, claims it by an atomic rename into its own folder, hashes it again without following a link, checks the digest and the declared size (a mismatch deletes it and downloads normally), and then inspects and commits as usual, with `downloaded:true`. The entry: `{app, version, file, urlHost, sha256, upstreamDigest, size, declaredSize, build, minOS, inspectMinOS, fetchedAt, approved:false}`: `size` is the bytes received, `declaredSize` what the source declared (the cap), `build` Stremio's `buildVersion` (Apollo: the app's `CFBundleVersion` from `inspect`), `minOS` Stremio's `minOSVersion` (Apollo declares none, so null) and `inspectMinOS` the Mach-O minimum OS `inspect` read for every app, which `sign` checks against the device's OS. `--approve --version <v>` is separate and offline: `--version` is required (`USAGE` without it, and `--version` alone is `USAGE`); it takes exactly that manifest entry for the app (`NOT_FETCHED` if the version is not there; no "newest" guessing), re-hashes the stored file against the manifest (`DIGEST_MISMATCH`, `IPA_MISSING`), re-inspects it, then sets `approved:true` and `approvedAt` and prints what the owner approves: `version`, `build` (its own field), `size` and `declaredSize`, `minOS`/`inspectMinOS`, both hashes (`sha256`, `upstreamDigest`) and the `inspect` summary (idempotent: `alreadyApproved`). Refetching bytes that match an earlier entry keeps its approval. `sign` refuses an entry that is not approved or whose file no longer hashes to `sha256` (built); `ManifestStore.path(of:)` refuses a `file` outside `<app>/<version>/<name>`. Codes: `USAGE`, `SOURCE_NOT_ALLOWED`, `SOURCE_INVALID`, `UPSTREAM_DIGEST_MISSING`, `FETCH_NETWORK`, `FETCH_TIMEOUT`, `FETCH_HTTP_ERROR`, `REDIRECT_NOT_ALLOWED`, `DOWNLOAD_TOO_LARGE`, `SIZE_MISMATCH`, `DIGEST_MISMATCH`, `VERSION_CONTENT_CHANGED`, `NOT_FETCHED`, `IPA_MISSING`, `MANIFEST_INVALID`, `MANIFEST_WRITE_FAILED`, `CANCELLED`, plus the `inspect` codes. `DownloadFlow` bounds memory: the delegate counts every received block and cancels the task the moment the total passes the cap (the declared size, and 2 GiB absolute; `DOWNLOAD_TOO_LARGE`), whatever the consumer is doing, and it suspends the task when more than 4 MiB are waiting for the consumer and resumes it at 1 MiB or less; both decisions are made under one lock together with the enqueue, so a suspend always has its resume, and a consumer that finishes or is cancelled closes the flow and cancels the (possibly suspended) task instead of waiting for a resume. **Locking.** The download holds no `.op.lock`, so a long download never blocks the lab or another command; `--approve` still holds it for its whole run. The sweep runs in every fetch, needs no lock and works across processes: an entry younger than 60 s (real file time against real time, never `Services.clock`) is skipped, a loose `fetch-*` file is removed, a `fetch-*` folder with no `live.lock` is removed, one whose `live.lock` is held is alive and skipped, one whose `live.lock` can be taken is stale and removed, and a `staged-*` file older than 24 hours is removed. A run that finds its own `live.lock` unlinked between mkdtemp and the lock is `CANCELLED`. Residual: SIGKILL can leave a `fetch-*` folder in `tmp/` (the kernel drops its lock, so the next run sweeps it after a minute); the size cap is the declared size, so an index whose size is wrong fails with `DOWNLOAD_TOO_LARGE` or `SIZE_MISMATCH`.

**Network client.** Both client uses share one ephemeral `URLSession` setup (no cookies, no cache, timeouts, size caps) and differ in redirects. `fetch` downloads follow at most 3 redirects via a delegate, each hop https and on the source's host allowlist (a refused hop is `REDIRECT_NOT_ALLOWED`); its metadata GETs follow none and send no token (`HTTPRequest.bearer` is optional, `portal` always sets it); `updates` makes the same metadata GET through `SourceMetadata`, which `fetch` shares. `portal` follows none: a redirect is refused outright and its 3xx comes back as an `ASC_HTTP_ERROR`, because the bearer token must never follow one. For `portal`, every request and every `links.next` must be https to `api.appstoreconnect.apple.com` on one of the four list paths. `HTTPRequest` has a URL and a bearer token only (no method, no body); the single call site sets `GET`, and a test scans `Sources/` for any mutating method or body API. 429, 5xx and timeouts are retried at most twice (1 s then 3 s, or `Retry-After` capped at 10 s) within a 120 s limit; a cancelled run stops at the wait and is `CANCELLED`; at most 20 pages of 200 per list; response bodies capped at 4 MiB. `fetch` downloads stream to a temp file with CryptoKit incremental SHA-256 (system framework). Downloaded IPAs are untrusted data: extracted into their own empty directory; paths passed as arguments.

## 9. State layout and sharing

Layout unchanged: `$SIDELOAD_HOME` (default `~/.sideload`, 0700): `config.json` (0600), `secrets/`, `downloads/<app>/<version>/<file>` + `manifest.json` (schema 1, 0600; see "`fetch` flow" in section 8), `updates.json` (schema 1, 0600, written atomically with no lock, last writer wins: `{schema, apps{<app>{checkedAt, version, build, minOS, size, sha256, errorCode, errorAt, retryAfter}}}`, what `updates` last saw upstream. Advisory only: `fetch` always resolves the source again and every hash gate is unchanged. The last good values and `checkedAt` survive a failed check; `errorCode`/`errorAt`/`retryAfter` (seconds, at most a day) describe the last attempt only while it failed. A missing, oversized (64 KiB), unparseable or wrong-schema file reads as empty and is rewritten; an entry dated after now (the clock moved back), for an app the catalog does not know, or with a value that fails the resolver's own checks (`isSafeToken` version and build, a 64-hex digest, a size within `FetchLimits.maxIPABytes`, a numeric `minOS`, an upper-case error code) is dropped; no secrets), `builds/` (`carrier/` and `carrier-dd/` for `provision`, `signed/<app>/<device>/<Name>.app` for free `sign`, 0700 at every level; section 18), `logs/` (`canary.jsonl`, `status.jsonl`, `commands.log`), `tmp/`, `ledger.json` (0600), `secrets/p12/` (exported `.p12` masters, 0600, created by `export-cert`), `exports/` (Feather kits, created on first use; not one of the directories `ensureHome` creates), `asc/` (the owner-provided App Store Connect API key for `portal`: `key.json` with `keyId`, `issuerId`, `keyFile` (a bare `AuthKey_<KEYID>.p8` name) and an optional `role`, plus that key file; directory 0700 and files 0600, owned by the user and not symlinks, else `ASC_KEY_PERMISSIONS`; not created by `ensureHome`; never read, printed or committed by agents), `evidence/` (opt-in canary bundles, created on first use; not one of the directories `ensureHome` creates) `profiles/free/<app>/<device>/<uuid>.mobileprovision` (free-team development profiles from `provision`, directories 0700 and files 0600; they contain device IDs, so they are never printed or committed; created on first use) and `backups/<device>/<app>/<stamp>/` (app-data backups from `slot lend`, directories 0700 and files 0600, created on first use; they hold session tokens, so they are secrets-class: never printed, logged, in the ledger or committed, and `check-secrets` refuses a `backups` path segment; section 18, "App data"). `canary.jsonl` lines carry `ts, status, code, device` (last 4), `xcodeVersion, guard, durationMs` and, since the evidence work, `macosVersion, iosVersion, certFp` (first 8 hex of the certificate's SHA-1) and `certNotAfter` (`YYYY-MM-DD`); the new keys are optional, a line stays under 512 bytes, and the blocked gate reads only `status`. Config gains `bundleIdPrefix` (now `io.github.dividedby`). Home inside any git work tree is refused (`HOME_IN_GIT_WORKTREE`); `FREE_TEAM_SELECTED` and `CONFIG_INVALID` validation unchanged; parse errors never echo file content. Swift loading is deliberately stricter than Node: a field of the wrong type (e.g. `minFreeGB: "3"`, a non-object device entry) is `CONFIG_INVALID` naming the key path, never the value; unknown keys (including `null` ones) survive rewrites, while `null` for a known key reads as absent.

**Ledger.** `ledger.json` (schema 1, kept apart from the owner-edited `config.json`) holds `certificates[{fp8,team,notBefore,notAfter,firstSeen,lastSeen,valid,present}]`, `profiles[{uuid,team,applicationId,wildcard,created,expires,deviceCount,deviceTails,certFp8s,source,firstSeen,lastSeen,present}]` and `exports[{id,createdAt,certFp8,profileUuid,p12File,p12Sha256Prefix,encryption,passwordItem,kitPath,verified}]` (written by `export-cert`), plus unknown top-level keys, preserved. No password, private key, full fingerprint, identity name or full device ID: `fp8` is the first 8 hex of the SHA-1, `deviceTails` the last 4 characters of each UDID. Only the paid team is recorded (first OU is the locked team and no OU is deny-listed); the free team's certificates and profiles are counted in `ignored*` and dropped. `ledger refresh` marks everything it did not see this time `present: false` (certificates also `valid: false`) and keeps it as history; only `present` entries feed expiry items, so a profile deleted from Xcode's folder stops warning but stays referenceable from an export. `valid` means seen, trusted for code signing and unexpired. A file that does not parse, or has another schema, is `LEDGER_INVALID` and its content is never echoed. Profile UUIDs are written whole (not secret) and masked to their last four characters in command output by the `Redactor`.

**Retention and `clean`.** `clean [--yes]` (`Commands/Clean.swift`, `CleanBackups.swift`, `CleanDownloads.swift`) is the one command that deletes under `downloads/` and `backups/`; it never touches `builds/`, `tmp/` (the `renewed-profile-*` folders stay), `profiles/`, Xcode's folders or `secrets/`. **`downloads/`:** per app it keeps every version `ledger.installs[]` records for the app (any device, present or not), the newest approved version (`ManifestEntry.older` order, the one `sign` picks), the approved version before it, and the single newest unapproved version while it is newer than the newest approved one (or nothing is approved): it is waiting for the owner's `--approve`. Every other version's `downloads/<app>/<version>/` folder is deleted, older unapproved ones included. Their `manifest.json` entries stay, since the version and SHA-256 of everything downloaded are the record, and gain `prunedAt` (optional, ISO-8601). Order under `.op.lock`: one atomic manifest write that marks every entry about to lose its folder, then the folders, so a crash leaves a marked entry whose file may still exist and a rerun finishes it without re-marking. A pruned entry counts as not on disk: `ManifestStore.hasFile` is false (so `refresh` keeps its `RENEW_VERSION_CHANGED` handling), `sign` answers `IPA_PRUNED` and names `fetch`, `fetch --approve` answers `IPA_PRUNED`, and the menu's Add app / Update confirm stops. A later `fetch` of that version downloads it again (a leftover file is not trusted), checks the same SHA-256 and replaces the entry without `prunedAt`, keeping the approval. **`backups/`:** see section 18, "App data", retention.

**Safe sharing between app, CLI, and launchd** (no architect-level design needed; small mechanisms):
1. **Atomic writes.** Every file is written to `<file>.<pid>.<rand>.tmp` (`O_EXCL`, 0600), `fsync`, `rename`. Readers never lock and never see a partial file.
2. **Config mutation lock.** `ConfigStore.update { cfg in ... }` takes `flock(LOCK_EX)` on `$SIDELOAD_HOME/.config.lock` (bounded retry with `LOCK_NB`, 5 s, then `BUSY`), re-reads, mutates, atomically writes. Prevents lost updates between `device save`, `status --notify` (`lastNotified`) and the app. `flock` is released by the kernel if the process dies.
3. **Operation lock.** `canary`, `sign`, `install`, `export-cert`, `fetch --approve` take a non-blocking exclusive `flock` on `.op.lock` for their whole run, and `fetch` without `--approve` takes it only to record a verified download (section 8); a second concurrent run returns `OPERATION_IN_PROGRESS` instead of racing portal state or derived data. `.op.lock` is also the shared lock for any signing with the free team 6ZU5Z6ZKK7: mobile-safari-lab takes the same file (dividedby/mobile-safari-lab#63, sideload #2), so the two tools never run `xcodebuild` provisioning or `codesign` with that identity at once. It is the only ordering mechanism with the lab (no process probing such as `pgrep`): a BSD `flock` with `LOCK_EX|LOCK_NB`, held by the lab (through a Perl flock helper) around its WDA build and signing spans, and by sideload around each free-team command. The lab never creates `~/.sideload`; sideload owns the directory and the file. The free-team commands (`provision`, free `sign`, `install`, `refresh`, `app remove`) take it non-blocking; a busy lock is a skip for auto-refresh only (it retries 30 minutes later); a manual run reports `OPERATION_IN_PROGRESS` (section 18).
4. **Ledger lock.** `LedgerStore.update` takes `flock(LOCK_EX)` on `$SIDELOAD_HOME/.ledger.lock` (the same bounded retry, 5 s, then `BUSY`), re-reads, mutates, writes atomically; a failed write is `LEDGER_WRITE_FAILED`. Separate from the config lock, so `device save` and `ledger refresh` never wait on each other.
5. **Append-only logs.** `canary.jsonl`/`status.jsonl`/`refresh.jsonl` (the last rotated at 1 MiB) are single-write `O_APPEND` lines (short, under the pipe-atomic size).

The app links `SideloadCore` and calls the same command functions in-process; it never spawns the `sideload` binary. Home is a local filesystem, so `flock` semantics hold.

## 10. Guard, classification, doctor, canary

**Team lock and guard** (ported unchanged for the paid context): identities match on certificate OU, never name; for the paid context OU 6ZU5Z6ZKK7 is a deny-list entry. Before any device contact: `codesign -dvv <app>` must show `TeamIdentifier=7AGMPUPP64` (`FREE_TEAM_SELECTED`/`WRONG_TEAM`/`GUARD_FAILED`); `security cms -D -i embedded.mobileprovision` must show team 7AGMPUPP64 and the device UDID in `ProvisionedDevices` (`DEVICE_NOT_IN_PROFILE`). The profile plist is parsed with `PropertyListSerialization`, not regex (a deliberate improvement; fixtures pin behavior).

**Guard context (section 18; built).** `Guard.run(context:)` takes `.paid` (the above, unchanged) or `.free`. `.free` requires: the `codesign` and profile team are 6ZU5Z6ZKK7; `application-identifier` equals `6ZU5Z6ZKK7.<id>` exactly (a free team has no wildcard); `<id>` is under `<bundleIdPrefix>.free.`; the device UDID is in `ProvisionedDevices`; the pinned certificate is in `DeveloperCertificates`; and no `.appex` remains in the bundle. Anything else stops before any device contact (codes in section 18). The context is chosen per app (`apps.<a>.team: "free"`), never by fallback, and a paid-context guard still rejects the free OU.

**Classification** is a pure `InstallClassifier` over a leaf-walk of the devicectl JSON plus stderr: code forms (hex, signed, unsigned) matched only under code-like keys for bare numbers.

| Signal | Status | Meaning |
|---|---|---|
| exit 0, outcome not `failed`, JSON lists the bundle id | `working` | Apple fixed it |
| 0xe8008018 or "identity used to sign the executable is no longer valid" | `blocked` | known account-side defect (support case open) |
| 0xe8008015 / 0xe8008016 / 0xe800801c | `blocked` if guard passed, else `error` | provisional, community-sourced |
| timeout, locked, not connected, disk full, output limit, exit 0 but unlisted (`INSTALL_UNCONFIRMED`), unknown | `error` | unrelated; raw code returned |

`BuildClassifier` maps overflow → `OUTPUT_LIMIT`, timeout → `BUILD_TIMEOUT`, spawn error or non-zero exit → `BUILD_FAILED` with up to three unique `error:` lines (300 chars each).

**doctor** checks (xcode, clt, cert, cert-free, device, appletv, disk) keep their semantics (`cert-free` is an `info` row per valid free-team identity, fp8 and expiry only, absent when there is none): `doctor.ok` false only on a `fail`; Apple TV `not-paired` is `info`; disk warns under 5 GB, fails under 2 GB (`statfs`).

**canary flow** (steps 1-9 unchanged from Node, verified against `canary.mjs`): preflight (cert + device) → snapshot apps before → `xcodebuild` Debug with `DEVELOPMENT_TEAM=7AGMPUPP64`, `PRODUCT_BUNDLE_IDENTIFIER=io.github.dividedby.sideload.canary`, `-allowProvisioningUpdates`, 10 min timeout, 128 MiB output cap → guard → `devicectl device install app` (120 s) → classify (save one scrubbed install JSON on first non-working run, device names/hostnames scrubbed) → uninstall only if this run added it → snapshot after, warn `unexpected-app-delta` → ambiguous-install cleanup of the exact canary ID only → append to `logs/canary.jsonl`. Sideload never deletes portal objects.

**Blank-project control.** The canary is already the control the support case asks for: a one-source-file SwiftUI app with no entitlements, no capabilities and no extensions (`canary/`), built with automatic signing for the paid team. A failure on it cannot come from the app's contents, so no separate blank project is needed.

**Evidence step.** With `--evidence`, after the log line, a `blocked` or `error` result writes `$SIDELOAD_HOME/evidence/canary-<ts>/` (0700) with `evidence.json` (schema 2) and `evidence.txt` (0600), for the owner to attach to an open Apple Developer Support case by hand; sideload sends nothing. `appleCase` is the optional `appleSupportCase` string from `config.json` (6 to 20 digits, else left out), null when unset. Contents: run (status, code, reason when the filter admits it, guard, duration); environment (macOS from `sw_vers`, Xcode, iOS version and build from `devicectl list devices` `deviceProperties.osVersionNumber` / `osBuildUpdate`, null when absent); `keychainCertificate` (the valid paid-team certificate with the latest expiry that the keychain would offer Xcode, which is not proof of what Xcode signed with: OU, validity, 8-hex fingerprint); the embedded profile (team, creation and expiry, device count, whether this device and that certificate are in it); the codesign team; and the install result (classification, exit code, timeout, outcome, the reduced `errorChain`, admitted stderr lines, and `omitted {nodes, messages, stderrLines}`; section 7). On the real device (2026-10-20) the chain is `com.apple.dt.CoreDeviceError` 3002, `IXUserPresentableErrorDomain` 14 (description, failure reason and a recovery suggestion that carries the signature template), `MIInstallerErrorDomain` 13 (`LegacyErrorString ApplicationVerificationFailed`, a `LibMISErrorNumber` and the template as its description, which becomes `codeSignature`); the depth 1 recovery suggestion contains the path, so it is counted under `omitted.messages`. The device listing runs at most once per run and only after the guard passed, so a failed guard still makes exactly two `xcrun` calls. A bundle name collision or an I/O error is the warning `EVIDENCE_WRITE_FAILED`; neither it nor a redaction failure changes the canary `status` or exit code.

## 11. Expiry checks (launchd; built)

User agent `io.github.dividedby.sideload.status`: `ProgramArguments [<abs path>/sideload, status, --notify]`, `RunAtLoad true`, `StartCalendarInterval` daily 09:00, `ProcessType Background`, `LowPriorityIO true`, `LimitLoadToSessionType Aqua`, stderr to `logs/launchd-status.err`. No `KeepAlive`, no `StartInterval`: it runs for a second and exits. `status --print-agent [--binary <abs path>]` prints the plist and the owner's commands; the owner reviews, copies the binary to a user-level path, and runs `launchctl bootstrap gui/<uid>`. sideload never installs it. It shares `AgentPlist` with the refresh agent (`refresh --print-agent`, section 18): `AgentPlist.Agent` (`.refresh`, `.status`) carries the label, arguments, schedule (an interval or a daily `StartCalendarInterval`), `RunAtLoad` and the stderr file, and the refresh plist text is unchanged. There is no kill-switch file for this agent; `launchctl bootout` removes it. Built.

The items come from `ExpiryItems.compute(ledger, now)` (the same list `ledger` prints; for paid certificates and profiles `ok` above 60 days, `warn` at 60 or fewer, `critical` at 14 or fewer, `expired` once `notAfter` has passed; whole days, rounded down; free installs use the 3/1-day levels in section 18), so `status` reads the ledger and never the keychain or the profile folders; `ledger refresh` keeps it current.

`--notify` (built; `Commands/StatusNotify.swift`) fires when a paid item crosses 60 or 14 days, or a free install crosses 3 or 1 days (section 18), or an item expires (threshold 0), or an app-data restore is pending (threshold 0), once per threshold per item, tracked as `lastNotified[key] = threshold` in config via `ConfigStore.update`. Keys: `install <app> @ <alias>`, `cert <fp8>`, `profile …<tail4>`, `restore <app> @ <alias>` (aliases through `printableAlias`; never an ID, device name or identity name). An item's threshold comes from the level `status` already computes (`ExpiryItem.level`: installs by exact time left, so 2.5 days is threshold 3; paid items by whole days, rounded down). It notifies when the current threshold is below the stored one or none is stored; an item above every threshold (renewed) has its key removed, and a stored value below the current one (renewed into a higher bracket) is lifted to it without a notification, so the next crossing fires. Keys of the four kinds whose item is gone are pruned, only when both the ledger and the config were read; other keys are left alone. All due items share one notification, soonest `notAfter` first and restores last, cut at 160 characters with `+N more` (every due item is recorded, including those folded in). The notification is posted by `osascript` through the runner as before (`Notifier`, the text passed as `argv`, never part of the script; `+` is now an allowed character). The new thresholds are written only after a successful post (`NOTIFY_FAILED` otherwise, `ok` stays true, the next run tries again); removals are written either way; the write re-reads the stored values inside `store.update` and keeps the lower one. A config that cannot be read posts nothing (`NOTIFY_SKIPPED`); one that cannot be written is `NOTIFY_STATE_NOT_SAVED`. Nothing due makes no `osascript` call. A bare CLI is not an app bundle, so `UNUserNotificationCenter` is not available to it. Needs a GUI session (the agent is `Aqua` only); fallback is `doctor` and the menu bar icon. This is the backstop for auto-refresh: `refresh --auto` notifies only its attempts, so a device it cannot see (`DEVICE_NOT_VISIBLE`) is skipped silently until the 3-day notification.

## 16. Risks

- **Process-group and signal behavior** is subtle; real-process tests (section 13) are the guard. Any change to the runner needs the full runner suite.
- **Security.framework ACL churn**: ad-hoc rebuilds trigger keychain prompts; mitigated by rarity of password/export use and by keeping `status` on public-certificate reads. If prompts become intrusive, fall back to `security` CLI for the password item with `security -i` stdin input.
- **`SecCertificateCopyValues` availability** (spike); DER-reader fallback is planned.
- **Clipboard exposure** (`--copy-password`): the password is on the general pasteboard for up to 90 s. Mitigations: the item is marked concealed and transient (clipboard managers that honour the convention skip it), it is cleared only while the change count is still ours, a signal during the hold ends it early (see below) and the pasteboard is cleared at once, and the owner runs the flag only when ready to paste. Residual: SIGKILL or a crash leaves it until overwritten; a clipboard tool that ignores the markers can read it; Universal Clipboard sends it to the owner's other devices (that is the point) and whether the concealed/transient markers change that handoff is unverified (first real run). With `--copy-password` the object always carries `clipboardCleared` and `clipboardHoldInterrupted`. `clipboardHoldInterrupted` is true when any signal was absorbed (during the write, the copy or the hold, including a failed copy). `clipboardCleared` is true when the password is off the pasteboard because sideload cleared it, or never put it there (a signal before the copy); it is false when sideload cleared nothing: the owner copied something else since, or the copy failed (the `PASTEBOARD_FAILED` warning says so; a clear is attempted either way and its result is what is reported). `clipboardHoldSeconds` appears only when the copy succeeded. Ctrl-C during the hold does not print `INTERRUPTED`: by then the kit exists and is recorded, so "re-run" would be wrong. Before the hold, stderr says where the kit is and that it is "recorded in ledger". The first SIGINT/SIGTERM/SIGHUP during the hold is absorbed by `HoldSignal` (the CLI handlers call `trip()` before the `Interrupt` path): the hold's wait ends, the main flow clears the pasteboard if it is still ours (`clipboardCleared` true or false) and emits the normal success object with `clipboardHoldInterrupted: true`, exit 0. From the start of the master `.p12` write until the kit is in place (`beginWriting` to `markCommitted`), every signal is absorbed and the main flow alone cleans up. A signal before the ledger write makes it remove the `.p12`, its temporary files and the staging folder (also beside `--out`), then end with `INTERRUPTED`; a later signal changes nothing. From the ledger write on, it finishes the move or rolls back. The signal handler never touches files. A signal before the write starts marks the export dead, and it then refuses to write anything. While the password is being copied (`beginCopy` to `copyFinished`) every signal is absorbed too, the hold then ends at once and the main flow clears the pasteboard, so the handler can never clear before the copy. After the kit is in place, the first signal ends or skips the hold; a second takes the `INTERRUPTED` path (the handler then clears the pasteboard if it is still ours), which reports `kit`, `ledgerRecorded` and `clipboardCleared` and never says to re-run. A signal that finds the export idle or dead (nothing written yet), or finished without a kit (`done(nil)`: it failed or was rolled back), also takes the `INTERRUPTED` path, which says to re-run because no kit exists. A signal after the command returned but before the result is printed (`done(kit)`) takes the same path and reports the kit. From the second absorbed signal while writing, committing or copying, one bounded stderr line says "finishing cleanup; kill -9 to force". The pasteboard's check-and-clear (and the copy) run under one lock in `ConcealedClipboard`, so a handler clear that arrives while main's clear is still in flight waits for it, for at most 500 ms, and then reports the outcome accurately (`alreadyCleared` counts as cleared; `changedSince` and `nothingCopied` say the clipboard did not hold the password). Residual risk: if main's AppKit clear takes longer than 500 ms, the handler gives up and the process exits with the clear still in flight; the `INTERRUPTED` object then has `clipboardCleared` null and tells the owner to copy something else to be sure. SIGKILL during writing can leave files behind.
- **Exported p12 uses legacy encryption** (3DES key bag, RC2-40 certificate bag, SHA-1 MAC; section 6 spike). OpenSSL 3 needs its legacy provider to read it, so Feather may refuse it; recorded per export, warned about, untested on device. Re-encrypting would need `openssl` and is not done. Creating a keychain file and changing its settings needs its password and shows a dialog; sideload's own tests avoid `SecKeychainSetSettings`.
- **Window-style `MenuBarExtra` refresh-on-open** unverified (spike); fallback defined.
- **Portal churn** during the open support case: one stable canary ID, creation only.
- **Custom `sign`** (appex ordering, profile-derived entitlements, appex main-binary flag on iOS 27, tvOS profile) is the riskiest component and cannot be tested until the account block clears. It is a candidate for architect review before it is built; it is outside the port scope.
- **`portal` and the key's role** (unverified): Apple's API docs list 403 for all four lists and do not say which key role may list certificates. A Developer-role key may be refused for `/v1/certificates`; the section then reports `ASC_FORBIDDEN` with the fix "switch the key to Admin" (an owner action in App Store Connect) while the other lists are still returned. Field names come from Apple's documentation, not a live call, so decoders ignore unknown keys and treat a missing one as null; the first owner-run `portal` is the real check. An `asc/` key is a long-lived credential on disk: keep it Developer-scoped unless certificates are needed, and revoke it when done. No JWT `scope` claim is sent (the accepted grammar is unverified).
- **Stremio source trust**: third-party index; mitigated by URL allowlist, own SHA-256, per-version owner approval, IPA inspection (`inspect`, section 8) before signing.
- **`inspect` reads untrusted archives** (section 8). The policy is layered (listing, size watch, `lstat` walk) because each layer has a gap on its own. Residual risks: (a) `ditto` may read an archive differently from `ZipListing` (two parsers), so the walk after extraction, not the listing, is what guarantees nothing is a link or outside the folder; (b) the size watch polls every 250 ms, so a fast bomb can write some hundreds of megabytes past the 4 GiB cap before `ditto` is stopped, and a deflate bomb is only bounded by that cap and the 180 s timeout, not by the headers; (c) `lipo`, `vtool` and `codesign` parse hostile Mach-O files, so a parser bug in an Apple tool is inside the trust boundary (the tools run as the owner, with a timeout and an output cap, and `codesign -d` verifies nothing and executes nothing); (d) the file is read by path at extraction after the listing and hash were taken from the open descriptor, so a swap in between is caught only by the identity re-check (`IPA_CHANGED`); (e) a SIGKILL or crash leaves an `inspect-*` folder in `tmp/` (no sweeper).
- **Apple TV pairing coexistence** with atvloadly (moot since atvloadly was retired on 2026-10-24) was "probably safe" at medium-low confidence; owner pairs only after an iPhone `working` canary, takes the pre-pairing notes in `docs/research/tvos-install.md`, does not update tvOS meanwhile.
- **launchd notifications** need a GUI session; fallback `doctor` and the menu icon.
- **Locked-keychain prompt** (unverified): the certificate read may show an unlock dialog if the login keychain is locked when launchd runs `status`. Test with a locked keychain before building the launchd job; if it prompts, `status` skips the certificate read while the keychain is locked (`SecKeychainGetStatus` or the error path) and reports the cert check as unknown.
- **Swift 6 strict concurrency vs C APIs** (`posix_spawn`, `poll`, `flock`) needs careful `@unchecked Sendable` islands, kept to the runner and lock types and each commented.

Each entry also records which Xcode folder it came from as a label (`folder`: `xcode-userdata`, `mobiledevice`, else `folder-N`), never a path. A run's `done` entries are removed only after its envelope was fully written: `provision` registers the settlement with `Services.postEmit` and the CLI runs it from `main.swift` only if `Interrupt.delivered` (the one object was written in full: no write error, no `EPIPE`, no signal), under the ledger lock, removing exactly that run's files and never a stray. A kill, a closed pipe or a failed write skips it and the next run reports them (a duplicate report is acceptable, an untracked file is not). Every `provision` envelope, whatever ends the run (usage, config, device, confirmation, a busy lock, the preflight, the build), carries `cachedProfilesFromEarlierRun: [{from, to, at, state, inTmp, folder}]` for the entries found when the ledger was read once at the start (read-only, no lock); an unreadable ledger adds `renewRecordUnreadable: true` instead of being skipped silently. An IPA built for another platform than the device is `PLATFORM_MISMATCH`.
  - **Strip.** `ExtensionStripper`: every `*.appex` outside `Extensions/` and `Watch/` wherever it sits (names compared without regard to case), `PlugIns/` if it ends up empty (else the warning `PLUGINS_NOT_EMPTY`), all of `Extensions/`, all of `Watch/` (a watch app's own appex goes with it and is not listed separately). Each bundle's Info.plist and `codesign -d --entitlements` are read first for `stripped[{path,bundleId,extensionPoint,entitlementKeys,appGroups}]` (an unreadable plist gives a null bundle ID and the warning `EXTENSION_UNREADABLE`; at most `maxExtensions` are listed, then `EXTENSIONS_TRUNCATED`; all are removed). `ExtensionStripper.remaining` then walks the app again, `lstat` only: any entry named `*.appex` (a symlink counts), a root `Extensions/` or `Watch/`, a nested `*.app` whose Info.plist says watchOS (`WKWatchKitApp`, `WKApplication`, `WKCompanionAppBundleIdentifier`, or WatchOS in `CFBundleSupportedPlatforms`), or a tree past the depth or entry limit, is `EXTENSION_REMAINS` (hard fail, the remaining paths listed).
  - **Rewrite.** `BundleRewriter.setBundleIdentifier` (`PropertyListSerialization`, same format, same mode, atomic) and `installProfile` (`_CodeSignature` and `embedded.mobileprovision` removed without following a link; the stored profile's exact bytes written, 0644).
  - **Entitlements.** `EntitlementReducer` over the main app's originals as `inspect` read them: always `application-identifier` (the profile's `<team>.<id>`) and `com.apple.developer.team-identifier` (the profile's team); `get-task-allow` always, with the profile's value (`profile.getTaskAllow`, already verified true; the original's is never copied and never listed as dropped); `keychain-access-groups` only if the original had at least one group, rewritten to the single group `6ZU5Z6ZKK7.<id>`. Every other original key is dropped and listed, sorted, in `droppedEntitlements`. The groups under `com.apple.security.application-groups` split into `appGroups.declaredByApp` (one `APP_GROUP_DROPPED` warning each, never a stop) and `appGroups.onlyInStrippedExtensions` (information only).
  - **Sign.** The bounds on every walker are the shared `limits.maxEntries * 2` and `maxTreeDepth`. `BundleSigner` first refuses nested code it does not sign, so that nothing keeps a foreign signature (`NESTED_CODE_UNSUPPORTED`, the relative paths in the message and in `nestedCode`): any `*.app`, `*.xpc`, `*.appex` or `*.kext` at any depth, a `*.bundle` whose Info.plist names an executable that exists, and a loose Mach-O file (magic bytes, thin or universal, either byte order) that is not the app's own executable and not a `*.dylib`; inside a `*.framework` (the innermost one) the only Mach-O allowed besides dylibs is its own `CFBundleExecutable`, so a helper binary in a framework is refused too; no generic signing was added. Then nested `*.framework` folders and `*.dylib` files anywhere under the app, deepest first (ties by path), each `codesign -f -s <SHA-1 of the pinned identity> --timestamp=none <path>`; then `codesign -f -s <SHA-1> --timestamp=none --entitlements <plist> --generate-entitlement-der <app>`; then `codesign --verify --strict --deep <app>`. 300 s per signing call (a keychain prompt can wait), 120 s for the verify, 1 MiB output cap. The identity is always the 40-hex SHA-1; a name never reaches argv. Failures: `CODESIGN_FAILED` with `step` (`nested`, `app`, `verify`), `KEYCHAIN_LOCKED` for `errSecInternalComponent` or "User interaction is not allowed", `FREE_IDENTITY_MISSING` for "no identity found", `TOOL_FAILED` when codesign cannot start, `CANCELLED` when interrupted; the tool's text is never echoed.
  - **Guard.** `Guard.run(context: .free(FreeSigning(...)))` on the signed bundle, in the scratch folder, before anything is placed. Its code is the command's code when it fails (`WRONG_TEAM`, `GUARD_FAILED`, `PROFILE_INVALID`, `DEVICE_NOT_IN_PROFILE`, `PROFILE_CERT_MISMATCH`, `EXTENSION_REMAINS`, `BUNDLE_ID_NOT_ALLOWED`) and nothing is kept.
  - **Place and record.** `builds/signed/<app>/<device>/` is made 0700 at each level; the signed app is moved there with one `renamex_np`: `RENAME_EXCL` when nothing is there, else `RENAME_SWAP`, which exchanges the two atomically (the previous signed app ends up in the scratch folder and goes with it), so the destination is the old complete app or the new complete app. Then, under the ledger lock, `freeSigned[{id:"<device>/<app>", device, app, bundleId, version, sha256Prefix, profileUuid, profileExpires, certFp8, signedAt, path, strippedExtensions[{path,bundleId}], droppedEntitlements}]` replaces the entry for that key (`version` is the manifest version, `sha256Prefix` the first 8 hex of the IPA's SHA-256, `path` relative to `$SIDELOAD_HOME`; the key is written only when non-empty). Disk and ledger must agree: if the ledger write fails after the move, the placement is undone (after a swap, swapped back, so the previous app and its record stand; after a first placement, moved back out into the scratch folder, which is removed) and the error (`LEDGER_WRITE_FAILED`) carries `placed: false` with a fix to run `sign` again. If the undo itself fails the app stays in place and the error carries `placed: true`, `recorded: false` and the relative `signedPath`; running `sign` again records it.
  - **Output** (one object): `app`, `device`, `bundleId`, `version`, `build`, `profile{uuid,daysLeft}`, `stripped`, `droppedEntitlements`, `appGroups{declaredByApp,onlyInStrippedExtensions}`, `deviceOS{version,minimum,source}`, `warnings`, `sha256Prefix`, `pinnedFp8` and the relative `signed` path. No UDID, CoreDevice ID, device or identity name, absolute path or profile content. Warnings from `inspect` (for example `BUILD_VERSION_UNREADABLE`) are passed through.
  - **Tests** use runtime-built IPAs that mirror the three real apps (Stremio iOS with its one WidgetKit appex, Stremio tvOS with none, Apollo with its app group), the real `ditto`, `lipo`, `vtool` and ad hoc `codesign` (the pinned SHA-1 is carried out ad hoc; `TeamIdentifier` and the extracted leaf are scripted, as are `security cms -D` and `devicectl`), and a fake Runner for the signing order.

**Preflight** (manual and auto)
- **3 apps per device.** A new app needs `used < 3`, else `FREE_APP_LIMIT`; a reinstall is slot-neutral. "New" is what the device says (an app installed by hand, with no `installs[]` record, is a slot-neutral reinstall that then gets recorded). **What is counted (owner decision 2026-10-24, from mobile-safari-lab#63):**
  - `managed` = snapshot IDs in the `<prefix>.free.*` allowlist (`device info apps`).
  - **Other free-team apps are found by their installed profiles, not by `builtByDeveloper`.** `devicectl device info apps` marks TestFlight betas `builtByDeveloper: true` exactly like free-team apps (all 8 apps on the owner's iPhone showed identical flags), and no Apple tool shows an app's team from the app list, so the flag counted betas against the 3 slots (`used: 8`). One read-only `devicectl device profile list --type provisioning` (once per command, near the snapshot, 60 s timeout, free scope) lists each profile's `teamIdentifier` and `appIdentifier`. An installed app that is not ours counts when some profile has `teamIdentifier == 6ZU5Z6ZKK7` and `appIdentifier == 6ZU5Z6ZKK7.<its bundle ID>`; expired profiles count too (fail-safe), a free-team profile whose app is gone counts for nothing, and TestFlight profiles (other teams) never count. The document is parsed strictly (`info.outcome` success, `result.provisioningProfiles` an array of objects with string `teamIdentifier` and `appIdentifier`); anything else is a failed read. No code path calls `device profile install`, `remove` or `validate` (`DeviceCtl` refuses everything but that one `list` argv before a subprocess, and a test scans `Sources/`). Only counts are printed, never another team's IDs.
  - **The lab's app counts inside the slot lent to it.** The free-team apps found are split into `labApps` (WebDriverAgent, by `FreeTeamSigner.label(of:)`) and `otherNonLab` (SideStore, atvloadly's copy, ...). Terms (both counted from the ledger's slot records for this device, other than the app being installed or returned, whose room is the one being asked for): `lent` = records with `lentTo` set that the snapshot does not show (the app is gone and the lab holds the room; only these can hold the lab's app, and a `returning` record counts here until its install is confirmed); `pending` = the other used records the snapshot does not show (an install or other op of one of our other apps that may still land: not lent, and never holding the lab's app). Then:
    `unmanaged = max(freeSlotsReserved, otherNonLab + max(lent, labApps) - lent)` and `used = managed + unmanaged + lent + pending`, i.e. `managed + pending + max(lent + reserved, otherNonLab + max(lent, labApps))`. So a lent slot and the WebDriverAgent living in it count once (apollo + filler + WDA + lent 1 is 3, not 4), and a reserve of 1 that stands for WebDriverAgent is not added on top of it (reserve is a floor for the unmanaged part). Not lent, WebDriverAgent installed: it counts 1.
  - **Profile read failed or malformed:** `unmanaged = freeSlotsReserved`, so `used = managed + reserved + lent + pending`, as before the profile read existed. TestFlight and other developer-built apps are never counted from the JSON flag (`otherDeveloperApps` is printed for information only).
  - **installd is the backstop.** If the phone is really full, the install fails with installd's "maximum number of installed apps using a free developer profile", classified `FREE_APP_LIMIT`: the list it prints (`{( "6ZU5Z6ZKK7.<bundle id>", ... )}` in `NSLocalizedRecoverySuggestion`, under `CoreDeviceError 3002` > `MIInstallerErrorDomain 13`, `ApplicationVerificationFailed`) is authoritative (installd lists only free-profile apps), reduced to our IDs, a count per known signer and a count of the rest, never a foreign ID verbatim; it widens the reported `used`, with a fix that names the `device slots --reserved` value to set. A definite refusal closes the op (effect absent, a lent slot stays lent, nothing is pending), so the next command runs with no 435/645 s window.
  - **Output.** Every `slots` object (`install` and its `FREE_APP_LIMIT` errors, `slot return`, `app remove`; one builder, `AppSnapshot.Usage.json`) has the same keys: `limit`, `used`, `free`, `reserved`, `managed`, `unmanaged`, `lent`, `pending`, `otherDeveloperApps`, `otherFreeTeamApps`, `labApps`, `otherNonLab`, `profilesRead`. Counts are numbers; `otherFreeTeamApps`, `labApps` and `otherNonLab` are null when the profiles were not read; `profilesRead` is a bool; `unmanaged` follows the formula above. The `FREE_APP_LIMIT` errors add `installdList` and `unmanagedListed` on top, and a device with an out-of-range stored reserve prints the same keys null with `unknown: true`. The preflight `FREE_APP_LIMIT` message says whether the count used the profiles or only the reserve.
  - `freeSlotsReserved` is now a floor for free-team apps the profile read cannot show (or when it fails), mostly the Apple TV's atvloadly copy until it was removed on 2026-10-24 (the Apple TV's reserve is now 0).
- **10 App IDs per 7 days, shared, not queryable.** The ledger keeps `freeAppIds[{bundleId,epochStart}]` and assumes each App ID lives 7 days; a run with no live epoch counts as a new registration. A new registration is allowed only if recent + `freeTeam.reservedAppIds` (owner-set, default 4) + 1 <= 10. Manual runs need `--yes`; auto keeps a margin of 1. Xcode's limit error is `FREE_APP_ID_LIMIT`.
- Also: pinned certificate valid, keychain unlocked (`KEYCHAIN_LOCKED`), disk space, and an app-set snapshot whose delta is none (refresh) or exactly our ID (first install).

**`app remove`.** `sideload app remove --app <a> --device <d> --yes` uninstalls one sideload-managed install to free a slot (for the lab, dividedby/mobile-safari-lab#63, sideload #2). Owner-only (agents never pass `--yes`, never run it against a real device), allowlisted to `io.github.dividedby.free.*`, takes the shared lock, and records an `uninstall` op before the device call (see "Slot lending and the pending-operation model"), marking the install absent only when the snapshot afterwards shows the app gone. Built with `install` (step 7). The app is named with `--app <a>` as in the other free commands (the bundle ID is derived from the key, so only `<prefix>.free.*` can be named), and the output carries the warning `LAST_FREE_APP_REMOVED` when the snapshot shows no other free-team app (ours, reserved or shown developer-signed) that would remain: removing the last one clears the owner's developer trust (the lab's lesson), but with `--yes` it still proceeds. Order: usage, config, device and platform, `--yes`, `.op.lock`, `settleInFlight`, migration, the gate (any op in flight on the device is `SLOT_PENDING`), snapshot, settle, the intent, uninstall (free scope), snapshot (the list must lose exactly that app, else `UNEXPECTED_APP_DELTA` after the record is updated). An app not on the device is an ok no-op; a result that cannot be confirmed leaves the op pending (`UNINSTALL_RESULT_UNCERTAIN` or the op's code, with `retryAfter`).

**`install` built (step 7).** `install --app <a> --device <d> --yes`: usage, config, device and platform, `--yes`, `.op.lock`, the keychain read and `FreeIdentityGuard.settleInFlight`, the pin, then the `freeSigned` record (`NOT_SIGNED`; its `path` must be `builds/signed/<app>/<device>/<Name>.app`, its bundle ID ours), `profileExpires` (`PROFILE_EXPIRED`), `Guard.run(context: .free)` on the signed app (its code is the command's; an embedded profile that has expired is `PROFILE_EXPIRED` too), then the snapshot, the slot preflight, `devicectl device install app` (300 s, free scope), classification (`FreeInstallClassifier`: `FREE_APP_LIMIT`, `DEVICE_LOCKED`, `DEVICE_NOT_CONNECTED`, `DEVICE_NOT_PAIRED`, `UNTRUSTED_DEVELOPER` with the fix text Settings › General › VPN & Device Management › trust, `TIMEOUT`, `DISK_FULL`, `OUTPUT_LIMIT`, `TOOL_FAILED`, else `INSTALL_FAILED`; exit 0 that does not name the bundle is settled by the second snapshot), the second snapshot (delta exactly our ID for a new app, none for a reinstall, else `UNEXPECTED_APP_DELTA`, a hard stop reporting counts only) and the ledger. The install's op (`install` or `reinstall`) is written BEFORE the device call (a first install also writes its `installs[]` entry; a reinstall writes none until the table confirms the new build landed, so the entry never claims a renewal the device did not receive) and is settled by the table in "Slot lending and the pending-operation model": a result that cannot be confirmed stays pending (it reads present and counts as used until a snapshot after its window decides), and a definite failure with the app absent restores the prior entry. Any op in flight on the device is `SLOT_PENDING`. A slot lent to the lab is `APP_LENT`. A failed snapshot before is `SNAPSHOT_FAILED` with no install.

**Slot lending and the pending-operation model** (agreed with the owner and mobile-safari-lab#63). `devices.<d>.lendableApp` (an app key such as `stremio-ios`) is owner-set by `device lendable --alias <d> --app <a>|--none --yes`. `slot lend --device <alias>|--udid <id> --to lab` and `slot return --device|--udid` take `.op.lock` themselves, run `FreeIdentityGuard.settleInFlight` first, accept `--udid` only when it equals a saved device's UDID or CoreDevice ID (else `DEVICE_NOT_SAVED`; never echoed; a UDID given to `--device` is shown as its last four characters), and reach the device only through `DeviceCtl`'s free scope. No `--yes`: the lab runs them. `lend` uninstalls the lendable app, `return` reinstalls it from the `freeSigned` build through the `install` path (same pin, guard, preflight and delta). `install`, `app remove`, `slot lend`, `slot return` and `status` all run on one model, because they act on the same device and the same slots: one record per `<device>/<app>`, one gate, one evidence rule. The code is `Commands/SlotRule.swift` (pure: the table, windows, migration, projection, view), `Commands/SlotBook.swift` (the ledger side: gate, settle, intent, final) and `Commands/SlotState.swift` (constants and the write primitive). The 27-cell table below is tested cell by cell through every command in `SlotCellMatrixTests`, the per-command rows in `SlotMatrixTests`, and the whole by crash injection (`SlotCrashTests`), late landings (`SlotGraceTests`, `SlotTimeoutShapeTests`), migration (`SlotRuleTests`, `SlotMigrationTests`) and a random walk (`SlotWalkTests`).

**App data: backup on `slot lend`, restore on `slot return`** (owner decisions 2026-10-24). A lent app's sign-in lives in its data container, which the uninstall deletes, so the lab's lend would log the owner out. `AppDataBackup` (`Commands/AppDataBackup.swift`) saves and puts back that container with Apple's `devicectl` only: `device info files --domain-type appDataContainer --domain-identifier <id> --recurse`, `device copy from` and `device copy to`, one file per call, through `FreeDeviceCalls` (`listFiles`, `copyFrom`, `copyTo`: data results that never throw). **Allowlist.** `DeviceCtl` accepts exactly those three argument shapes (`requireAppDataCall`): the free scope only (`.paid` refuses all), `--domain-type` exactly `appDataContainer`, `--domain-identifier` equal to the scoped `<prefix>.free.*` ID, each flag once in the `flag value` form, no positional and no other flag (`--user`, `=` forms and extras are refused), a device path that is relative without `..`, `.`, empty parts, NUL or a leading dash, and a local path strictly under `$SIDELOAD_HOME/backups/` without `..`. Any argv or positional that names `copy` or `files` and is not one of the three shapes is `BUNDLE_ID_NOT_ALLOWED` before a subprocess. A Sources scan test pins that only `DeviceCtl.swift` and `FreeDevice.swift` build these vectors. **Where it runs.** The backup is read-only and not a slot operation: it runs in `lend` after L6 (the signed build is valid) and before L7 (the durable intent and the uninstall), only when the app is on the device (S0) and `apps.<a>.backupData` is not `false` (default true; an opt-out reports `dataBackedUp:false, dataBackupSkipped:true` with no warning). It never fails the lend: a failure is `dataBackedUp:false` plus a warning and the lend goes ahead (the lab must not be blocked; the loss is a sign-in). The restore runs in `return` row T7 after the delta check and outside the `RETURN_FAILED` steps; it is never run on the T0 or T3 no-op paths (a newer container could be overwritten). `install` never launches the app, so the restore precedes its first launch. The slot model (`slots[]`, gate, settle, windows, profile-based count) is unchanged. **Layout and ties.** `backups/<device>/<app>/<stamp>.partial/` is written, then renamed to `<stamp>/`; it holds `manifest.json` (`bundleId`, `version` of the `freeSigned` build, `lendSince`, `createdAt`, `complete`, `files[{path,size,sha256}]`, `restoredAt`, `supersededAt` once a later lend replaced it, and `uninstalledAt` once the lend took the app off the device) and `data/<relative path>`. `lendSince` is the `since` the lend's slot record carries: the SETTLED record's (`settled.after(app)?.since ?? now`, what `begin` keeps; the settle at S0 clears a lend it found undone, because the app was present once its window ended, and `begin` then starts a new one at `now`, so the record read before the settle must not be used), so a return restores only the newest finished backup with `lendSince == record.since` and `restoredAt` unset, and a stale backup is never restored after a newer lend that saved nothing. Only files are copied, in this order: `Library/Preferences` first (the sign-in lives there and must not be starved), then files whose listed size is known, then the rest, by path. Before any filesystem or device call the listing is cut down. A path that is not safe (absolute, a `..` or `.` part, an empty part, NUL or a backslash) is dropped and counted failed; so is a path that collides with an earlier one, compared with a full Unicode case fold (so `Σ`, `σ` and `ς` match) and NFD because the volume under `backups/` is APFS (the first in copy order is kept; a file whose folded name is also a folder's, such as `A` next to `a/x`, loses). Directories (an entry that is the parent of another entry, or that `metadata` marks as one) are never copied, and neither is anything under `Library/Caches` or `tmp`. **Nothing follows a link.** Every local path is built by one function that refuses a path that does not stay under `backups/`. Folder creation (`secureDirectory`) walks the path one part at a time with `lstat`, creates missing parts with `mkdir`, refuses a part that is a symlink or not a folder owned by the user, and sets mode 0700 through a descriptor opened with `O_NOFOLLOW`; a file is only ever chmodded the same way. Nothing is written over what is already at a destination. After every `copy from` the result is `lstat`ed: only a regular file stays, anything else (a symlink devicectl left, a folder) is removed and counted failed, and it is never opened, chmodded or written through. The restore checks every part of each local path (backup folder, manifest, data file) with `lstat` before reading it, so a link planted inside a backup cannot make it push a file from outside; the prune does the same before it deletes. A size that differs from the listing is retried once, then failed. Caps: 200 files, 256 MiB (checked against the listed size before a file is asked for when it is known, and again on the copied size) and 120 s of wall time in all. The wall time includes what the Runner adds when a call hangs: `DeviceCtl` gives it `--timeout` + 15 s (`DeviceCtl.runnerMarginSec`) and the Runner needs up to 8 more seconds to stop the child (2 s SIGTERM-to-SIGKILL grace, 1 s drain, 5 s reaping; `PosixSpawnRunner.worstCaseOverrunSec`), so each call's `--timeout` is the smaller of 60 s for the listing or 30 s for a copy and what is left of the allowance minus those 23 s, read from the constants, checked before every call, and no call is started with under 5 s. One entry that cannot be saved locally (a name over the filesystem's length limit, say) is counted failed and skipped; the rest of the backup is kept. The 120 s can be overrun by under a second of local work (hashing, pruning). A listing with nothing usable in it (only unsafe or colliding paths) is a failed backup with a warning, not an empty success. The restore has its own 120 s: it re-hashes each local file against the manifest (a changed file is not pushed), pushes file by file, relists and compares presence and, where devicectl lists a size, sizes; only a full match sets `restoredAt` and prunes. The newest 2 finished backups are kept per device and app, and every `.partial` folder is swept, after each backup and each verified restore. A crash mid-backup leaves a `.partial` folder and an untouched device; a crash mid-restore leaves the install recorded, `restoredAt` unset, the backup kept and the container partly restored (no automatic recovery; the owner retries with `slot restore`, below). No quit of the running app is attempted (`devicectl` cannot), so hash and size prove copy fidelity, not freshness. **Output** (additive; counts and booleans, never a path or file name): `lend` L8 gains `dataBackedUp`, `dataFiles`, `dataFilesFailed` (and `dataBackupSkipped`); `return` T7 gains `dataRestored`, `dataFilesRestored`, `dataFilesFailed`. **`dataFailures`** (sideload#2): when `dataFilesFailed` is above 0, `lend`, `return` and `slot restore` also print `dataFailures`, an object of the non-zero counts by reason (absent when nothing failed, like `dataBackupSkipped`); its values always sum to `dataFilesFailed`, because a failed file is counted only through one `Failures` value. The keys are a fixed set of words, never a path, file name or text from `devicectl`: `unsafePath` (the listing named a path that is not a safe relative path), `nameCollision` (a case, Unicode-form or file-against-folder clash with an earlier entry), `fileCap` (over 200 files), `sizeLimit` (over 256 MiB by the listing, once copied, or skipped after the cap was reached), `timeLimit` (no allowance left for a call, or skipped after it ran out), `localError` (this Mac: the folder, the destination, permissions, the hash), `notRegularFile` (the copy left a link, folder or other non-regular file, which is removed), `sizeMismatch` (the size differed from the listing on both tries), and for a failed `copy from` call `copyTimeout` (the Runner's timeout or `devicectl`'s own `--timeout`), `copyDeviceLocked`, `copyDeviceNotConnected`, `copyNotRun` (never started, threw, or refused by the allowlist) `copyNoResult` (the call reported success but left nothing on this Mac for a listed file; the listing's directory rows, marked by metadata or the parent of another entry, are never copied or counted, but an empty directory the listing does not mark counts here) and `copyOther` (everything else: a non-zero exit, an exit 0 with `info.outcome` other than `success`, an output overflow, a signal kill). The call's class comes from the same fixed classifier as `install` (`FreeInstallClassifier`); its locked and not-connected patterns are loose and read stderr, so the class is best effort (a mislabel is possible, a leak is not, since no text is kept). `devicectl`'s numeric error codes are not reported. The restore counts its failures on the same keys, in the order its checks run: `unsafePath` (the manifest names an unsafe path), `localError` (the file in the backup is not a plain regular file, or its size or hash no longer matches the manifest), `timeLimit` (no allowance left, or skipped after it ran out), the `copy*` classes for the `copy to` call, and `notOnDevice` (restore only: pushed, but the relisting did not show the file or showed another size; `dataFilesRestored` already leaves them out). The progress lines read `app data backup: 10 file(s) saved, 3 failed (copyTimeout 2, notRegularFile 1)` and `app data restore: 11 file(s) restored, 1 failed (copyOther 1)` (reasons in the declared order, none when nothing failed). `RESTORE_FAILED` carries `dataFailures` in its data, like the counts. A relisting that cannot be read (`DATA_RESTORE_UNVERIFIED`) has no failed file, so no `dataFailures`. A call that exits 0 but reports a failure is a failed call: a document that is not an object, a top-level `error` (a null one is none), an `info` that is not an object, or an `info.outcome` other than `success`. The listing calls run the same check before `parseListing`, so a listing with such an `error` or `info` is refused too (the backup is `DATA_BACKUP_FAILED`, a restore relisting `DATA_RESTORE_UNVERIFIED`). No document, or one with neither `info.outcome` nor `error`, still counts as success; the backup checks the file left and the restore relists. Warnings only, never failures: `DATA_BACKUP_FAILED` (listing or every copy failed, or the folder could not be written), `DATA_BACKUP_INCOMPLETE`, `DATA_RESTORE_INCOMPLETE`, `DATA_RESTORE_UNVERIFIED` (pushed but the relisting could not be read), `DATA_RESTORE_PARTIAL_BACKUP`. **Secrets-class.** Backups hold session tokens: directories 0700, files 0600, never printed, logged (progress lines carry counts only), in JSON, in the ledger or in the repo (`ensureHome` already refuses a home inside a work tree; `check-secrets` also refuses a `backups` path segment). The `devicectl` argv, with file names, still goes to `logs/commands.log` like every subprocess (inside the 0700 home). Worst case (every call hanging to the Runner's kill) the backup adds at most the 120 s allowance (about 2 minutes) to a lend and the restore to a return, tested with a clock; typical is seconds, so the lab raises its timeout. **The listing** (`devicectl device info files --domain-type appDataContainer --recurse --json-output`, checked on a real iPhone) is `result.files[]` with `name`, `relativePath`, `metadata` and `resources` per entry, directories included; the path is `relativePath` and the size is read from `metadata` when it has one. **Checked on a device** 2026-10-25 (mobile-safari-lab#63, Stage 2, iPhone on Wi-Fi, `stremio-ios`): backup, then `copy to` after the reinstall; the app was still signed in with its library and add-ons. Three backups that day skipped 2, 2 and 1 of 12–13 files, each after exactly one failed `copy from` (no cap, filter, size retry or budget was involved); the cause is not known yet (a guess: files the running app creates and deletes between the listing and the copy), and per-reason failure counts are built (sideload#2; `dataFailures` below), so the next live run says which reason it was. Still unverified: `copy from` of every kind of file, and the file mode and ownership `copy to` leaves on the device. Tests: `AppDataAllowlistTests`, `AppDataBackupTests` (a simulated container behind the fake runner; modes, no leak of content, names or paths, failure and partial cases, budget, the lend tie, crash leftovers, retention).

**Manual restore: `slot restore --device <alias> [--app <app>] --yes`** (owner-only; the lab never runs it). `slot return` finds its backup only by `lendSince == record.since`, and the slot record's `since` is cleared once the return completes, so a failed or interrupted restore (manifest `restoredAt` unset, backup kept) had no retry. `SlotRestore` (`Commands/SlotRestore.swift`) is that retry. It is not a slot operation: it writes nothing to the ledger, installs and uninstalls nothing, and the debug hook does not apply to it. `--app` defaults to the device's `lendableApp` (neither: `USAGE`); `--udid` and `--to` are `USAGE`. **Order:** usage; saved alias (`DEVICE_NOT_SAVED`); app; `--yes` (`CONFIRM_REQUIRED`, before any lock or subprocess); `.op.lock` (`OPERATION_IN_PROGRESS`); `FreeSession.settle` (marker and keychain first, as every free-team command: `KEYCHAIN_LOCKED`, `FREE_CERT_CHANGED`); ledger `loadMigrated` and the gate (`SLOT_PENDING`, no device call); a lend record for this app in any phase (`ALREADY_LENT`, fix `slot return` first); the pending backup (a local read, no device call); one `trySnapshot` whose list must hold the app's bundle ID (`SNAPSHOT_FAILED` or its classified code; `APP_NOT_INSTALLED`, fix: run `slot return` or `install` first); then `AppDataBackup.push`, the body the return's restore uses. **Pending backup.** The NEWEST finished folder of `backups/<alias>/<app>/` alone decides, never an older fallback, with the same plain-path checks as the return: it must have a readable manifest with this app's `bundleId`, `restoredAt` unset, `supersededAt` unset and `uninstalledAt` set. Every file the manifest lists must also be a readable regular file whose every part under the backup folder is real (`isPlain`, then an `O_NOFOLLOW` open), checked before any device call (and each file again just before its push; `devicectl copy to` then opens the source by path, so a same-user swap inside the 0700 home between that check and the copy is not prevented). Otherwise `NO_PENDING_RESTORE` with `restored`, `superseded`, `unreadable`, `notUninstalled` booleans, each set on its own (a lend undone by a settle and run again leaves a backup both superseded and unmarked, and both are reported; the message names the most relevant reason, in the order restored, superseded, not uninstalled, unreadable). `notUninstalled`: no `uninstalledAt`, its lend never took the app off the device or it predates the mark, with a message and fix that say so. `unreadable`: anything that cannot be read, listed or `lstat`ed, or a link at any level (the device's folder, the app's folder, the backup folder, the manifest, `data/` or any folder or file an entry points into, dangling or not). The folder chain is walked from `backups/` one part at a time with `lstat`, so a link is never followed and never read as "no backup": only a real folder chain that stops at a missing part, or an app folder with no finished backup, is that (the fix says there is nothing to restore, or that the owner signs in again). **Supersede rule.** The return's `candidate` ties a backup to its lend; the retry has no `since`, so staleness is recorded instead: `slot lend` marks every older, unrestored finished backup of the app (`lendSince` at least a second before this lend's `since`, so a resumed lend does not supersede its own backup) with `supersededAt`, right before L7, whether or not the new backup succeeded or was skipped (`backupData:false` included). It rewrites the manifest atomically at 0600 after the same plain checks, swallows every error, and never fails the lend. **Uninstalled mark.** A lend saves its backup before the uninstall, so a lend whose uninstall fails outright (L9) or never lands leaves a newest backup that is older than the app's live data. `uninstalledAt` is what tells that apart: `markUninstalled` sets it wherever a snapshot shows the app off the device while the slot is lent: at L8 (the uninstall confirmed, including an uncertain result the snapshot resolved to absent), at L3 (a later lend's settle found the app gone and recorded the slot `lent`), and at T4 (the return found the app absent and the slot lent), before the return's intent and install, so a return that stops before its own restore (a crash around `return.final`, whose rerun is a no-op) still leaves the backup to `slot restore`. A lend that is undone (L9, or a settle that finds the app present) never sets it, so `slot restore` refuses its backup (`notUninstalled`; a later lend also marks it `supersededAt`); no failure path has to remember to mark anything. The return's own restore does not need the mark. A crash between the lend's confirmed uninstall and its mark (around `lend.final`) is covered the same way: the slot is recorded `lent`, so the return's T4 marks it. Backups from before the field are refused by `slot restore` (the return still restores its own lend). **Result.** Verified: `ok`, `dataRestored:true`, `dataFilesRestored`, `dataFilesFailed` (and `warnings`, for instance `DATA_RESTORE_PARTIAL_BACKUP`), `restoredAt` set, old backups pruned, this one kept. Not verified: `RESTORE_FAILED` with `cause` (`DATA_RESTORE_INCOMPLETE` when a file failed or did not verify, `DATA_RESTORE_UNVERIFIED` when only the relisting could not be read), `dataRestored:false`, `dataFilesRestored`, `dataFilesFailed`, `dataFailures` (when a file failed), `kept:true`, `warnings`; the backup is kept and `restoredAt` stays unset, and a rerun is safe because a push overwrites. Output carries counts and booleans only. **Time.** The restore's own `Budget` applies unchanged (120 s in all, per-call `min(30, left - 23)`, no call under 5 s), so the worst case is 120 s plus the one snapshot call. SIGINT or SIGTERM take the existing interrupt path, the flock frees on exit and the manifest stays unrestored, so a rerun resumes. **Surfaced** by `status` and the menu (`pendingRestores`, `DATA_RESTORE_PENDING`; see "`status` expiry and pending restores"); the `DATA_RESTORE_*` warnings of `slot return` also name the command, with the `--device` and `--app` to retry, in their `fix`. Residual risk: an unrestored newest backup, after the owner reinstalled and used the app, would overwrite newer data; the command is owner-run and explicit. **Not yet run on a device** (`slot restore` itself; the same `copy to` as the return, checked live 2026-10-25). Tests: `SlotRestoreTests`.

**Retention: `clean`** (owner decision 2026-10-30). The newest 2 backups per device and app (`AppDataBackup.prune`, at lend and after a verified restore) stay as they are. `clean --yes` adds an age rule, `CleanCommand.retentionDays` = 14, over `backups/<alias>/<app>/<stamp>/`. **A saved alias:** a backup whose `restoredAt` or `supersededAt` is more than 14 days before now is deleted; the age is counted from that marker (the later of the two when both are set), never from `createdAt`. A backup with neither marker is never deleted, so a backup `slot restore` would still push (the newest finished one, unrestored, unsuperseded, uninstalled) is always kept; `clean` also asks `AppDataBackup.pending` and skips that folder. **A device that is busy** (`DeviceRemove.refusal`: the lab holds a slot, a lend or return is unsettled, or any operation is inside its window) is skipped whole and counted in `devicesSkippedBusy`; the command does not fail. **An alias no longer saved** (`device remove` keeps backups, and `slot restore` cannot run for it): a backup whose newest of `createdAt`, `restoredAt`, `supersededAt` and `uninstalledAt` is more than 14 days old is deleted. **A manifest that is missing, unreadable, or not a plain file** keeps its backup (`unreadable`). **`.partial` folders** (written by an interrupted lend; none can be in progress under the lock) are deleted when their modification time is more than 14 days old, for any alias, and kept otherwise; the lend's own `prune` still sweeps them sooner for its device and app. **Links:** only real folders are entered or deleted (`backups/`, alias, app and backup folders are `lstat`ed, the chain is re-checked before each deletion, a link is counted in `linksSkipped` and left alone). After a deletion the emptied app and alias folders are removed with `rmdir` (never recursive). The output is counts (`deleted`, `kept`, `unreadable`, `failed`, `devicesSkippedBusy`, `linksSkipped`, and `byReason` of `restored`, `superseded`, `unsavedAlias`, `partial`): no alias, path, folder or file name. A preview computes the same numbers and deletes nothing.

**`SIDELOAD_TEST_FORCE_SLOT` (debug builds only).** So mobile-safari-lab can test how it handles `SLOT_PENDING` and `RETURN_FAILED` without a device, `SlotCommand.run` has a hook compiled in only when `DEBUG` is defined (`#if DEBUG`; `swift build`/`swift test` define it, release builds do not). While the variable is set and non-empty, `slot lend|return` answer after the alias is resolved and before `.op.lock`, the ledger, the keychain or the device (nothing is written, no subprocess runs), and the answer is the same on every call (stateless). `pending`: `SLOT_PENDING` built by `SlotBook.pendingError` from a synthetic `install` op (`retryAfter` 645, `freed:0`, `state:"pending"`, `uncertain:true`, `lent:false`, `app`, `op:"install"`, plus `action` and `device`). `return-failed` on `slot return`: `RETURN_FAILED` with the shape `giveBack` prints for a definite failure with the app still lent (`cause:"DEVICE_LOCKED"`, `state:"lent"`, `lent:true`, `app`). `return-failed` on `slot lend`, and any other value, are `USAGE`. `app` is the device's `lendableApp`, else `filler`. Tests (`SlotForceHookTests`) check the key sets against a real `SLOT_PENDING` and a real `RETURN_FAILED`, `USAGE` for what it refuses, and, against the built debug `sideload`, that no lock file, ledger change or other file appears. A release build must not contain it: `scripts/check.sh` runs `swift build -c release --product sideload`, requires that `strings` finds no `SIDELOAD_TEST_FORCE_SLOT` in the binary, and runs `slot return --device <saved> ` with the variable set in a temp home whose `.op.lock` the script itself holds, so a release binary must answer `OPERATION_IN_PROGRESS` (never `SLOT_PENDING`) without reaching the keychain or a device. Give the lab the release binary.

*Record.* `ledger.slots[{id:"<device>/<app>", device, app, presence, lentTo, since, op, seenAt}]` (schema stays 1; written only when non-empty). `presence` is `present`, `absent` or `unknown` (only with an op in flight, migrated from a legacy pending record). `lentTo` (`lab`) and `since` say who the slot is lent to. `op` is the device operation that may still be in flight: `{kind: install|reinstall|uninstall, by: install|lend|return|remove, startedAt, window}`. `startedAt` is the clock read when the op is written, rounded up; `window` is the longest the op can run plus `settleGrace` (300 s), in seconds: 645 for an install or reinstall (the 300 s `devicectl` timeout, 45 s of runner allowance, 300 s of grace) and 435 for an uninstall (90 + 45 + 300). The window used is `max(stored, current)`, so changed constants never shorten a pending record. Derived: `holds = lentTo ∧ op = nil ∧ presence = absent` (the lab holds the slot) and `used = ¬(presence = absent ∧ op = nil ∧ lentTo = nil)` (a pending or lent slot is used, never free). `installs[]` keeps the install's metadata, but its `present` and `opAt`, and all of `lent[]`, are a **projection** of the slots, rewritten in the same atomic write as every change (`present = presence ≠ absent ∨ op ≠ nil`, `opAt = op.startedAt`; `lent[].state` is `lent` when the lab holds the slot, `returning` for an install or reinstall op, `lending` otherwise), so an older build reads something safe.

*One evidence rule.* A snapshot's `takenAt` is the clock read before `device info apps` starts. A record with an `op` is settled (i) by any valid snapshot with `takenAt ≥ startedAt + window`: presence then comes from the snapshot and the op is cleared; (ii) inside the window, only by the snapshot taken in the same run right after the op (S1), through the table below. A snapshot that cannot be read, or is not a complete listing, never settles anything. A record with no op takes its presence from any valid snapshot, and a present app clears `lentTo`. The result of a device call is *unknown* in every shape `FreeDeviceCalls.uncertain` names: the runner's kill, `devicectl`'s own `--timeout` (a non-zero exit classified `TIMEOUT`), an output overflow, a signal kill (no exit code, no spawn error), a call that threw, and an exit 0 that does not name the bundle; a spawn error never ran anything and is a definite failure. In the table P and A mean that presence becomes present / absent and the op is cleared (P also clears `lentTo`); *keep* leaves the op and its `startedAt`, so the window keeps running. Reaching the op's target state is monotone for an install (present) and an uninstall (absent): nothing left in flight can undo it, so the target state settles the op even when its result is unknown. A reinstall's target equals its start state, so only a definite result settles it: **a reinstall is never settled by presence alone.**

| op kind, result | S1 present | S1 absent | S1 unreadable |
|---|---|---|---|
| install, success | P | keep (`INSTALL_UNCONFIRMED`) | keep |
| install, failure | P (`INSTALL_RESULT_UNCERTAIN`) | A (the prior `installs[]` entry is restored) | keep |
| install, unknown | P | keep | keep |
| reinstall, success | P | keep (`UNEXPECTED_APP_DELTA`) | keep |
| reinstall, failure | P | A (`UNEXPECTED_APP_DELTA`) | keep |
| reinstall, unknown | keep | keep | keep |
| uninstall, success | keep (`UNEXPECTED_APP_DELTA`) | A | keep |
| uninstall, failure | P | A (`UNINSTALL_RESULT_UNCERTAIN`) | keep |
| uninstall, unknown | keep | A | keep |

*Gate.* After the lock, `FreeIdentityGuard.settleInFlight` and the migration, `install`, `slot lend`, `slot return` and `app remove` look at every record on the device. If any has an `op` with `now < startedAt + window` the answer is `SLOT_PENDING` {retryAfter, freed:0, uncertain:true, app, op, state, lent} with no device call and no change. `op` is `install`, `reinstall` or `uninstall`; `state` is the lab's word (`lending` / `returning`) for a lend record and `pending` for any other op. The gate is per device, not per record: one op in flight per device keeps the app-set delta checks and the slot counts sound. `INSTALL_PENDING` no longer exists.

*Pipeline.* Every command runs the same steps: **G** gate, **S0** snapshot, **W1** `<cmd>.settle` (rule i on every record on the device; written only if something changes), the decision and checks, **W2** `<cmd>.intent` (the op, plus `lentTo`/`since` for a lend and, for a first install only, its `installs[]` entry; durable BEFORE every device call, with `startedAt` read at the write), the device call, **S1**, **W3** `<cmd>.final` (rule ii, the table; `keep` writes nothing). `migrate` is a write point of its own. The test hook `Services.afterDurableWrite` fires after each write. A crash after W1 leaves the record settled and nothing new; after W2 an op in flight (`SLOT_PENDING` inside the window, settled by the first S0 after it); after W3 the command done. A process killed before W2 never touched the device.

*Migration.* `SlotRule.migrate` runs under `.op.lock` before the gate and writes once, at `migrate`. It runs when `slots` is missing, or when an older build has written `installs[]` or `lent[]` since (the legacy fields no longer equal the projection; compared key by key). `status` and the menu migrate in memory and write nothing. A legacy `lent{state:lent}` becomes absent with `lentTo`; `lent{lending, opAt}` becomes unknown with an uninstall op at `opAt`; `lent{returning, opAt}` unknown with an install op at `opAt`; a stateless `lent`, a pending one with no `opAt` (a `returning` one keeps the longer install window) or one in a state this build does not know becomes unknown with `lentTo` and an op at *now* (fail-safe: one wait of up to 435 s from the first run; it does not slide, because the migration is persisted); `installs{present, opAt}` becomes present with a **reinstall** op at `opAt` (the strictest kind); `installs{present}` present; `installs{present:false}` with no lend and no `opAt` absent; with an `opAt` it is pending too (unknown presence, a reinstall op at `opAt`), used until its window passes. A lend record wins over an `installs[]` entry for the same app.

*Invariants.* I1: every device mutation is preceded by a durable W2 whose `startedAt` is at or after the wall clock at the write. I2: at most one op per device inside its window; W2 is never written while another op is pending on that device. I3: inside the window only that run's own S1 changes a record, and only through the table; a reinstall is never settled by presence alone. I4: `lentTo ∧ op = nil ⇒ presence = absent`. I5: `presence = absent ∧ op = nil` means the app is not on the device now and not once every op in flight has landed (so the same for `holds`). I6: `status` free is never more than the true free count once everything has landed. I7: `lentTo` is written only in a run where the signed build was valid and unexpired. I8: after every write, `installs[].present/opAt` and `lent[]` equal the projection of `slots`. I9: no output holds a UDID, a CoreDevice ID or a foreign ID. `SlotWalkTests` checks all nine against the simulated device after every step of 20 seeded walks of 500 steps (every command and both lendable apps, every unknown-result shape, failed and malformed snapshots, a crash at every write point, late landings, clock jumps of 0 to 1000 s, a signed build that comes and goes), and I5 and I6 again once everything in flight has landed. Reverting either of the two fixes below makes it fail on every seed.

*Outcome table.* S0 is the snapshot before (also the settle snapshot), S1 the snapshot after. The pre-op rows make no device mutation; the other columns are W3's effect.

*Preflight.* `used` is the managed IDs in S0, plus the used records on the device that S0 does not show (other than the app itself: a lent slot counts for a new app, and a return is that slot coming back), plus the unmanaged part of the profile-based count above (`max(freeSlotsReserved, otherNonLab + max(lent, labApps) - lent)`; the reserve alone when the profile read fails). Builds on `builtByDeveloper` are gone: TestFlight betas never count. The installd `FREE_APP_LIMIT` list is read as before and widens `used`.

*The two bugs this model fixes.* (a) A reinstall that ended unknown while the app was still listed was settled present by the listing alone; a `lend` then uninstalled the app, the reinstall landed late and put it back, and the lab held a slot whose app was on the device. Now the op is kept (table: reinstall, unknown), the `lend` is `SLOT_PENDING`, and the late landing changes nothing. (b) `lend` and `app remove` looked only at their own app's record, so a plain install of another app that was still in flight was invisible to them; the gate is per device.

*Other rules.* `slot lend` refuses before uninstalling unless a valid `freeSigned` build with an unexpired profile exists. While a slot is lent on a device (any state) it counts as used for a new app of ours (`FREE_APP_LIMIT`) and in `status`. A hand-installed own ID is a reinstall (slot-neutral) and is recorded present. `LAST_FREE_APP_REMOVED` counts only our other `<prefix>.free.*` installs and WebDriverAgent or SideStore apps as keeping the trust; the reserve and unlabelled developer-signed apps do not, so it errs on the side of warning. An unknown or tampered `lent[].app` (WebDriverAgent, say) reaches no device: `slot return` fails `RETURN_FAILED` and the settle skips it.

*Snapshot validity* (`AppSnapshot.parse`). A snapshot is evidence only if it is a top-level object with `info.outcome == "success"` and `result.apps` an array whose every element is an object with a non-empty string `bundleIdentifier`. IDs come only from those elements. Anything else (no `result.apps`, `apps` not an array, one malformed element, a failed outcome) is `SNAPSHOT_FAILED`; `apps: []` is a valid empty device.

*`status`.* `lent[]` is `{app,device,to,state,since,holds}` with `holds` true only for `lent`; `slots.devices[]` is `{alias,limit:3,used,free,reserved,apps[],lent:{app,state}|null,pending,retryAfter}`: every used record counts once (`used` includes the reserve), `pending` is true while any record has an op that is not settled, and `retryAfter` is the seconds until the last open window on the device ends (null when none is open). Each pending lend record adds the warning `SLOT_STATE_PENDING` (fix: `slot lend` or `slot return --device <alias>` settles it). `status` reads the ledger and config only, with no devicectl call, and migrates in memory without writing. **Lab contract:** the slot is the lab's only after an ok `slot lend`, or when `holds` is true; a pending state is never free, and `SLOT_PENDING` means retry after `retryAfter` seconds. The published JSON changes only by addition: `lend` gains `dataBackedUp`, `dataFiles`, `dataFilesFailed` (and `dataBackupSkipped`, and `dataFailures` when a file failed), `return` gains `dataRestored`, `dataFilesRestored`, `dataFilesFailed` (and `dataFailures` when a file failed), and the new `DATA_BACKUP_*` / `DATA_RESTORE_*` codes are warnings only (the lab gets no new failure; "App data" above); `lend` and `return` may answer `SLOT_PENDING` because of a pending plain install, reinstall or remove on the device, `SLOT_PENDING` data gains `op` and its `state` may be `pending`, and `slots.devices[]` gains `retryAfter`; the codes, `lent[].state` and `holds` are unchanged. The menu bar app counts a record as used whatever its state (a signed app counts only when it has no slot record; with a live read the count is `AppSnapshot.usage` with the lent and pending records the snapshot does not show as outside use), never as free. With `ledger.json` unreadable (or, for one device, its stored `freeSlotsReserved` out of range, `reserved` then null too), the slots are unknown, never guessed: each `slots.devices[]` row has `unknown: true` with `used`, `free`, `apps`, `lent`, `pending` and `retryAfter` null, top-level `lent` is null, and the menu shows "slots unknown" with no slot free.

**Ledger and expiry.** Schema stays 1 with new optional top-level `installs[]`, `slots[]` and `freeAppIds[]` (older builds preserve them); free profiles stay out of `profiles`. `installs[{id:"<device>/<app>", device, deviceTail, app, bundleId, team, profileUuid, profileCreated, profileExpires, certFp8, version, sha256Prefix, signedAt, installedAt, strippedExtensions, droppedEntitlements, present, refresh{lastAttempt,lastResult,lastCode,consecutiveFailures,nextEligible,attemptsByDay,suspended}, opAt}]` (`present` and `opAt` are projected from `slots[]`). `ExpiryItems` gains `kind: install` (`stremio @ iphone`) at `profileExpires` (built: the free certificate's expiry is not in the ledger and `status` never reads the keychain, so only the profile's date is used; `doctor` shows the certificate's) with free thresholds separate from the paid 60/14: `ok` above 3 days, `warn` at 3 or fewer (auto-refresh should already have run), `critical` at 1 or fewer, then `expired`. `status` gains `installs[{id,device,app,notAfter,daysLeft,level,autoRefresh,lastResult,nextEligible,suspended}]` (step 8, built: see "`status` expiry and pending restores" below) and, for the lab, `lent`, `slots.devices[{alias,limit,used,free,reserved,apps[],lent,pending,retryAfter}]` and `appIdsLast7Days` (step 7, built). The menu bar's Apps card per device reads `installs[]` and `slots[]` plus a live app list per visible device (section 12, "Live presence"): days left, a red "Renewal failed · <code>" from `refresh.lastResult`, the state of an app that is gone or lent; Renew, Install, Remove and the lendable setting run from the card behind the inline confirm (section 12).

**`status` expiry and pending restores (step 8, built).** `ExpiryItems.installs(ledger, devices:, now:)` gives one `kind: install` item (`<app> @ <device>`) per `installs[]` record that is `present` on a device still saved in config (a retired device's records are ignored), at the record's `profileExpires` (the free certificate's expiry is not recorded in the ledger and `status` never reads the keychain, so the certificate bound of `min(profileExpires, certNotAfter)` is not applied; `doctor` shows the certificate's expiry), with `FreeInstallExpiry`'s levels (exact remaining time: `warn` at 3 days or less, `critical` at 1 or less, `expired` at or past zero). `status` merges them into `items` (soonest first), so `state` follows them; `ledger` keeps printing the paid items only. `installs[]` lists the same records with the refresh bookkeeping (`lastResult`, `nextEligible`, `suspended`) and the device's `autoRefresh` opt-in. Each install at `warn` or `critical` adds an `INSTALL_EXPIRING` warning and each expired one `INSTALL_EXPIRED`, with the owner's `sideload refresh --device <d> --app <a> --yes` as the fix. `PendingRestores.find` runs, per saved device and free app that resolves for it, the same newest-backup check `slot restore` makes (`AppDataBackup.pending`: the manifest is parsed and the files it lists are `lstat`ed and opened, never read), skipping a device with an operation still inside its window on any slot (exactly what `slot restore`'s gate refuses; a stale op past its window does not hide the flag), an app whose slot is lent (that backup is the return's), and an app whose slot was last seen (`seenAt`) less than `PendingRestores.settleWindow` (300 s: the restore's 120 s plus a margin) ago: `slot return` records the slot returned at `return.final` and only then pushes the data, so without the window a lock-free read would flag every return's restore while it runs. A failed restore therefore shows up to 5 minutes after the return. Each found backup is a `pendingRestores` entry `{device, app}` and a `DATA_RESTORE_PENDING` warning whose fix is the owner's `slot restore`; it does not change `state`. The menu's local load (`MenuLoader.loadLocal`) adds the same warning as a notice. With the ledger or the config unreadable, `installs` and `pendingRestores` are null (which apps are lent, or which devices are saved, is unknown). No lock, no subprocess, no write; output is aliases, app names, dates and counts only. Tests: `StatusInstallsTests`, the status cases in `SlotRestoreTests`.

**Auto-refresh**
- **Trigger: a user launchd agent**, not the menu bar app (no timers, section 12; it works while the app is closed): `~/Library/LaunchAgents/io.github.dividedby.sideload.refresh.plist`, `ProgramArguments [~/.local/bin/sideload, refresh, --auto]`, `StartInterval 1800`, `RunAtLoad false`, `ProcessType Background`, `LowPriorityIO true`, `LimitLoadToSessionType Aqua`, no `KeepAlive`, stderr to `logs/launchd-refresh.err`. `refresh --print-agent` prints it (built, under "`refresh --print-agent` built" below); the owner copies the binary to `~/.local/bin` (section 17 Q1) and runs `launchctl bootstrap gui/$UID`; sideload never installs it. Missed intervals coalesce into one run on wake; in a dark wake the device is usually invisible, which is a skip, not an attempt. It reads files only unless something is eligible; only then does it call `devicectl list devices`.
- **Per install, all must hold:** (1) no `refresh.disabled` kill-switch file; (2) the device has `autoRefresh: true`, set only by owner `device auto-refresh --alias d --on --yes` (`Confirmation.standing(device)` is built only from that flag); (3) the install came from an owner-confirmed run, is `present` and not `suspended`; (4) 5 days or fewer left, `now >= nextEligible`, at most 2 attempts per install and 4 per device per local day; (5) the device is paired and available over **Wi-Fi (network) OR USB (wired)** transport (owner decision; the exact transport values are spike S1); (6) the shared operation lock is free (non-blocking; busy is a logged skip); (7) the full preflight passes, and any failure means no action.
- Then provision, sign, Guard, install, snapshot. If the app is gone, mark it `present:false` and stop: auto mode never installs a missing app and never uninstalls.
- **Backoff and stop.** Transient failures (`DEVICE_LOCKED`, `TIMEOUT`, device invisible at install time): 30 min, then 1, 2, 4, 8 h, capped at 12 h. Permanent failures **suspend** the install until a manual success: `FREE_CERT_CHANGED`, account sign-in, either limit, a guard failure or `PROFILE_INVALID`, `PROFILE_NOT_RENEWED` twice, an unexpected app delta. 20 minutes cap per run.
- **Log and notify.** One `logs/refresh.jsonl` line per decision (install, eligible or skip reason, step, code, duration, `newExpires`), plus `commands.log` for every exec. Every attempt also notifies through `osascript display notification`, built from aliases, integers and codes only ("stremio @ iphone refreshed, 7 d left" or "...failed DEVICE_LOCKED, next 14:30, 4 d left"), and so does an install that becomes suspended; skips and a busy lock are silent (built: "`refresh --auto` built" below).

**`refresh` built (step 9, manual)** (`Commands/Refresh.swift`, `Commands/RefreshPolicy.swift`; `refresh --device <alias> [--app <a>] [--within 1-6 | --force] --yes`; owner-run; first run on 2026-10-28 from the menu's Renew…; spike S5 passed 2026-10-30)
- **What it is.** The manual half of the loop above: for one saved device it renews the free-team installs that are close to expiring by running the existing `provision`, `sign` and `install` commands, in that order, per app, soonest expiry first. It does not wrap them in a lock: each step takes `.op.lock` itself (a whole-run hold would conflict with the steps' own non-blocking `flock` and keep the lab out for the length of the run), so the lab can sign between two steps; every step re-reads the keychain and the identity check catches a certificate change. A busy lock is `OPERATION_IN_PROGRESS` for that app: no wait, no retry, and the attempt is given back. `--auto` and `--print-agent` are the next sections.
- **Selection.** `--within` days (default 5, 1 to 6; `--force` is 6). 6 is a hard ceiling because a renewal must move the expiry by more than 24 hours (`PROFILE_NOT_RENEWED`). Candidates are the device's `installs[]` records (expiry: the device copy's `profileExpires`; a lent app: the `freeSigned` copy's), plus an own app with no record that has a `freeSigned` record and that the live snapshot shows (installed by hand, Stremio tvOS today). Its device copy's expiry is unknown (`sign` overwrites the signed copy's with the new profile's, so a sign whose install was blocked would read as fresh), so its install is always due: one slot-neutral reinstall records it, and the normal rules apply from then on. Provision and sign run first only if the `freeSigned` expiry is within the window. The device's app list is read once (`device info apps`, read-only) and only if an app that is not lent could be due. An app the device does not show is `NOT_PRESENT`: refresh never installs a new app. A signed app with no record that the device does not show is `NOT_INSTALLED` (an app nothing is known about is not listed unless named). When the device could not be read, every hand-installed app with a `freeSigned` record fails (`ok:false`) with the device's code, whether or not its signed copy is fresh, because the device copy's expiry is unknown: provision and sign run first only if the signed copy is within the window, and the install is skipped.
- **Which version.** The `sign` step signs the version recorded in the install's `installs[].version`, not the newest approved one (owner decision 2026-10-28), provided it is still a fetched, approved manifest entry whose IPA is on disk as a regular file (checked with `lstat`, no link followed; `sign` still hashes it). If it is not (the entry is gone, was never approved, or its file is missing), `refresh` falls back to the newest approved version, as `sign` does without a version, and adds the warning `RENEW_VERSION_CHANGED` naming both versions; a renewal is never failed for this. An app with no `installs[]` record (installed by hand) has no recorded version to keep, so it signs the newest approved version with no warning. A rerun that resumes after `sign` has no sign step and so no version to choose.
- **Steps and resume.** A rerun must not hit `PROFILE_NOT_RENEWED` because an earlier run got part-way. So from the ledger as it is: `provision` is skipped when the stored `freeProfiles.expires` is more than 24 hours past the device copy; `sign` is skipped when `freeSigned.profileUuid` equals the stored profile's; `install` always follows (the signed copy is then the fresh one). The filler is signed by `provision` (no `sign` step). A lent app gets provision and sign only: status `renewed-not-installed`, warning `APP_LENT`, no install and no device call (`slot return` puts the renewed copy back).
- **App IDs.** A renewal uses no new App ID. `provision` runs without `--renew`; only `PROFILE_NOT_RENEWED` is retried, once, with `renew: true` (never `registerDevice`). Each app reports `appIdNew` (from `provision`) and `appIdsLast7Days` (the ledger's live count). `FreeAppIdBudget` treats an epoch older than 7 days as new, so a renewal after a long gap can show `appIdNew: true` and spend budget; `FREE_APP_ID_LIMIT` stays the gate.
- **Gates.** Up front, read-only: `freeSuspended` stops the run with `FREE_CERT_CHANGED` (or `IDENTITY_CHECK_FAILED`) and refresh never clears it; a pending slot operation on the device (`SlotBook.pending` on the in-memory migration) is `SLOT_PENDING` with `retryAfter` and no work. Each install gates again; a `SLOT_PENDING` mid-run stops the device. The slot model (`slots[]`, the table of `SlotRule`, the windows) and the profile-based slot count are unchanged; refresh writes no slot.
- **Stops.** Fatal (stop; the rest are `skipped` with that code): `FREE_CERT_CHANGED`, `IDENTITY_CHECK_FAILED`, `FREE_IDENTITY_*`, `KEYCHAIN_LOCKED`, `ACCOUNT_NOT_SIGNED_IN`, `UNEXPECTED_APP_DELTA`, `SLOT_PENDING`, `RENEW_CROSS_VOLUME`, `PROFILE_MOVE_FAILED`, `PROFILES_UNREADABLE`, `DERIVED_DATA_NOT_CLEARED`, `LEDGER_WRITE_FAILED`, `LEDGER_INVALID`, `WRONG_TEAM`, `GUARD_FAILED`, `INTERRUPTED`, `CONFIG_*`. Everything else is that app's failure and the run goes on. `DEVICE_LOCKED`, `DEVICE_NOT_CONNECTED` and `DEVICE_NOT_PAIRED` (from the first snapshot or from an install) are not fatal because `provision` and `sign` need no device: they still run for every selected app, installs are skipped for the rest of the run, each such app's status is `failed`, with `steps.install: skipped`, `code` the device's code and a fix to rerun once the device is available (the rerun resumes at the install), and the result is `ok:false`.
- **Manual versus auto.** The daily caps (2 attempts per install, 4 per device, per local day) and `suspended` are for the automatic run (`refresh --auto`, below). A manual run warns (`ATTEMPT_CAP_EXCEEDED`, `INSTALL_SUSPENDED`), still records the attempt in the install's `refresh{}`, ignores `nextEligible`, and a success clears a suspension (`install` already does). An app with no `installs[]` record has no refresh fields, so nothing is recorded for it (no attempts, no `lastResult`) until its first successful install creates the record.
- **Ledger.** Only the install's `refresh{}`: before an app's first step `attemptsByDay[today] += 1` (days older than 7 are pruned) and `lastAttempt`; after, `lastResult` (`refreshed`, `renewed-not-installed` for a lent app whose signed copy was renewed, `failed`, or `skipped` for a busy lock, which also gives the attempt back; the menu's Cancel is the same with `lastCode: INTERRUPTED`: `RefreshPolicy.Result.cancelled`, used when the task is cancelled and a step fails with a code the cancellation can explain (`RefreshPolicy.isCancellation`: `INTERRUPTED` or an ordinary step code, not a permanent or fatal one, which keeps its own result), records no failure, no backoff and no suspension. A failure that comes back after Cancel was pressed (the task is cancelled) is recorded the same way, as skipped with `INTERRUPTED`, because the cancel killed the child; owner-confirmed 2026-10-28. The CLI never sees it, signals kill the process), `lastCode`, `consecutiveFailures`, `nextEligible` (the 30 m, 1, 2, 4, 8, 12 h ladder) and `suspended` (set by a failure that will not fix itself: `PROFILE_NOT_RENEWED`, `PROFILE_INVALID`, `FREE_CERT_CHANGED`, `IDENTITY_CHECK_FAILED`, `ACCOUNT_NOT_SIGNED_IN`, `FREE_APP_LIMIT`, `FREE_APP_ID_LIMIT`, `UNTRUSTED_DEVELOPER`, `UNEXPECTED_APP_DELTA`, `WRONG_TEAM`, `GUARD_FAILED`, ...). A hand-installed app has no record, so no attempts or `lastResult`, until its first successful install writes one; a failure before that writes nothing.
- **Result.** A cancelled run (the menu cancels its task) is `ok:false` with `INTERRUPTED`; the rest are `skipped` with that code. One object: `device`, `within`, `force`, `results[{app, status: renewed|renewed-not-installed|skipped|failed, steps{provision,sign,install: done|skipped|failed}, code, daysLeftBefore, daysLeftAfter, appIdNew, appIdsLast7Days, renewRetried, renew{}, retryAfter}]` (`renew` is the five `cachedProfiles*` keys of a `--renew` retry), `renewed`/`failed`/`skipped`, `appIdsLast7Days`, `warnings`, and `cachedProfilesFromEarlierRun` once at the top level. `ok:false` iff an app failed or a fatal stop; `errors[]` has one entry per failed app, its fix naming the manual step. Policy skips are `ok`. No UDID, device name or identity name appears. Two `--renew` retries in one process settle their `freeRenewMoves` after the envelope through `PostEmit.add`.

**`refresh --auto` built (step 9, auto)** (`Commands/RefreshAuto.swift`, `RefreshAutoPolicy.swift`, `RefreshLog.swift`, `Notifier.swift`; `refresh --auto`, no other option; run by the owner's launchd agent since 2026-10-29; spike S9 passed 2026-10-30)
- **What it is.** The command the launchd agent runs every 30 minutes. It is `refresh`'s `renew` with an auto context (`RefreshRun.auto`): the same `provision` then `sign` then `install` per app, each step taking `.op.lock` itself, the same one `--renew` retry of `PROFILE_NOT_RENEWED` (never `registerDevice`), the same ledger fields. It takes no option (`--device`, `--app`, `--within`, `--force`, `--yes`, `--print-agent` and `--binary` are `USAGE`): the window is 5 days, the devices are the ones with `autoRefresh: true` and a valid `freeSlotsReserved` (an opted-in device with an invalid reserve is a logged `CONFIG_INVALID` skip, and one of a platform none of our apps runs on a logged `PLATFORM_MISMATCH` skip; both are counted in `skipped`, neither is a failure), and `--yes` is not needed because the owner's opt-in and the kill switch are the standing confirmation. Agents never run it on a real device (Ask the owner first).
- **Gates, cheapest first** (`RefreshPolicy.runGate` for the run, `RefreshPolicy.autoGate` per install; both pure, the run reads what they are given). Whole run, all `ok:true` and silent: (1) the `$SIDELOAD_HOME/refresh.disabled` file exists, `KILL_SWITCH` (an unreadable path counts as present; nothing else is read); (2) the ledger has `freeSuspended`, `FREE_CERT_CHANGED` (an unreadable ledger is not a skip: the run is `ok:false` with `LEDGER_INVALID` and nothing runs); (3) one probe of `.op.lock` (acquire and release), busy is `OPERATION_IN_PROGRESS`, never a wait (an error from the probe that is not "busy", such as a lock file that cannot be opened, is reported as a failure with its own code, `ok:false`, and nothing runs). A config that cannot be read after these gates is likewise a failure that ends the run. Then the opted-in devices, and per install of each, in this order, one skip code each: `NOT_RECORDED` (no `installs[]` record but a signed copy: the hand-installed app, which only the owner's manual run records; an app with no record at all is not listed), `LENT`, `NOT_PRESENT`, `SUSPENDED`, `SLOT_PENDING` (any slot operation in flight on the device), `SIGNED_VERSION_DIFFERS` (the `freeSigned` build is not the installed version: a half-done update, which only the owner finishes with Install update), `NOT_DUE` (more than 5 days left), `BACKOFF` (`now < nextEligible`), `INSTALL_CAP` (2 attempts today for the install), `DEVICE_CAP` (4 today across the device), `RECENT_ATTEMPT` (last attempt under 5 minutes ago). Only if an install is still a candidate does the run call `devicectl list devices`, once for all devices; a device that `DeviceList.autoEligible` rejects (absent, unpaired, not `connected`, transport not `network` or `wired`) is `DEVICE_NOT_VISIBLE`: not an attempt, not a failure. A lent app is `LENT` before `NOT_PRESENT` because a lend also sets `present:false`.
- **The path.** For a device that passed: the app list is read once (`device info apps`; for a `disconnected` device this is the probe, and a failed read makes the device `DEVICE_NOT_VISIBLE`), an app it does not show is `NOT_PRESENT` and not put back, then the apps go soonest expiry first. Before each app the run is stopped (an earlier fatal code, a cancelled task) or past its deadline (`DEADLINE`: no new app 20 minutes after the start; not an attempt, not a failure; the app just waits for the next run), then the app is gated again against a fresh ledger read (the lab, or this run's earlier apps, may have changed it). Then `renew` counts the attempt, runs the steps and applies the result with `RefreshPolicy.applying`, exactly as for a manual run, except: no `ATTEMPT_CAP_EXCEEDED` or `INSTALL_SUSPENDED` warnings (the gates already held), and **no version fallback**: the installed version (`installs[].version`) must be a fetched, approved manifest entry whose file is on disk (checked before `provision` whenever a sign step is needed), else the app fails with `VERSION_NOT_AVAILABLE` and no step runs. That failure is not in `permanentCodes`: it counts the attempt, backs off (30 m, 1, 2, 4, 8, 12 h) and notifies, and clears when the owner fetches and approves that version again (or a manual run signs the newest). A busy lock in the middle of an app, whatever step, is a skip and not a failure (the attempt is given back, no backoff, silent) and ends the run; the next run resumes at the step that did not finish. A failure that is fatal for the whole team or machine, so it ends the run for every device (`FREE_CERT_CHANGED`, `IDENTITY_CHECK_FAILED`, `FREE_IDENTITY_*`, `KEYCHAIN_LOCKED`, `ACCOUNT_NOT_SIGNED_IN`, `LEDGER_INVALID`, `LEDGER_WRITE_FAILED`, `CONFIG_INVALID`, `CONFIG_MISSING`, `WRONG_TEAM`, `GUARD_FAILED`, ... `RefreshPolicy.fatalCodes`) with the rest skipped under its code: a certificate, keychain, account, ledger, config, wrong-team or guard failure, `RefreshPolicy.stopsWholeRun`. `SLOT_PENDING` and `UNEXPECTED_APP_DELTA` are about one device and stop that device only; the next device goes on. A permanent failure sets `suspended` (see "Ledger" above); only a manual success clears it, and `refresh --auto` never does.
- **Result.** One object: `auto: true`, `devices[{alias, results[{app, status, steps, code, daysLeftBefore, daysLeftAfter, appIdNew, ...}]}]` (the per-app shape of the manual run; a skipped app carries `daysLeftBefore` when its expiry is known), `skipped{code: count}` (every skipped result by code, and a whole-run skip as `{reason: 1}`), `warnings`, `errors[]`. `ok:false` (exit 1) iff a renewal failed or a configuration or ledger error stopped the run; a busy lock, the kill switch, a suspension, nothing due and a device that is not visible are `ok:true`. launchd has no `KeepAlive`, so a failure is not retried before the next interval; the ledger's backoff decides.
- **Log.** `logs/refresh.jsonl` (`Paths.refreshLog`; one `O_APPEND` line per record, 0600, moved to `refresh.jsonl.1` at 1 MiB so about 2 MiB at most). Every line has `ts`, `run` (a random 8-hex id per invocation) and `event`: `run` (one per invocation, last: `ok`, `durationMs`, counts, `skipped{}`, and `reason` for a whole-run skip), `install` (a decision other than `NOT_DUE`: `device` alias, `app`, `decision` `renew` or `skip`, `reason`, `daysLeft` when the install is known, `probe` (the failed app list's code) on a `DEVICE_NOT_VISIBLE` from a probe, and `stopped: true` when the skip was caused by a stop of the device or the run and not by the app's own gates; a device-level skip has no `app`), `step` (`provision`, `sign` or `install`: `ok`, `code`, `durationMs`, `renewRetried`) and `result` (`decision` = the status, `code`, `daysLeft`, `newExpires`, `nextEligible` after a failure, `suspended`, `notified`, `durationMs`). `RefreshLog.record` cleans every field itself, by its key. Only aliases, app names, numbers, timestamps and codes: a code that is not an upper-case word, or holds a run of 12 hex digits, is written `OTHER`; no device ID, device name, identity name, message or path. A write that fails is ignored. `commands.log` still has every exec.
- **Notifications.** `Notifier` runs `/usr/bin/osascript` through the `Runner` (10 s timeout, 4 KiB output cap): the script is three fixed `-e` lines (`on run argv`, `display notification (item 1 of argv) with title "sideload"`, `end run`) and the text is the argument, cleaned to letters, digits and ` @,.:-_` (at most 160, never starting with `-`). One per renewal attempt ("stremio-ios @ iphone refreshed, 7 d left"; "stremio-ios @ iphone failed DEVICE_LOCKED, next 14:30, 4 d left") and one more when the attempt made the install `suspended` ("... suspended after PROFILE_NOT_RENEWED, renew it by hand"). Skips, a busy lock and a cancelled run say nothing. A notification that fails (no permission, a timeout) is only `notified:false` in the log. Spike S9 (2026-10-30) posted one from the launchd job (`notified: true`, `osascript` exit 0).
- **Tests.** `RefreshAutoTests`: every gate and its order, one test per install gate through the whole command (no step, no `list devices`, no notification, no counter moved), the whole-run gates and their laziness, the kill switch, a busy lock before and during a run, the ladder and both caps across days on a hand-moved clock, suspended until a manual success, the one `--renew` retry, a certificate change stopping every device, `VERSION_NOT_AVAILABLE` in four forms, the pinned version, the deadline, one `list devices` for all devices and none when nothing is a candidate, no ID or name in the log, the envelope or a notification, the notifier's argument vector and its failure, log rotation and modes, and the command line.

**`refresh --print-agent` built (step 9, agent)** (`Commands/RefreshAgent.swift`: `AgentPlist.render`, `RefreshCommand.printAgent`; `refresh --print-agent [--binary <abs path>]`, no other option)
- **What it is.** Pure: it builds text. No `.op.lock`, no subprocess, no file written (`dispatch` answers it before `ensureHome`, so not even the home or the logs folder is created), no device, no config or ledger read. Agents may run it; they never run what it prints. One envelope (command `refresh`) with `label` (`io.github.dividedby.sideload.refresh`), `path` (`<user home>/Library/LaunchAgents/<label>.plist`), `plist` (the XML text), `install` (the owner's commands, in order) and `stop`. A relative `--binary` (default `<user home>/.local/bin/sideload`), one with a control character, `--binary` without `--print-agent`, or `--print-agent` with any other refresh option is `USAGE`.
- **The plist.** `Label`; `ProgramArguments [<binary>, refresh, --auto]`; `StartInterval 1800` (missed intervals coalesce on wake); `RunAtLoad false`; `ProcessType Background`; `LowPriorityIO true`; `LimitLoadToSessionType Aqua` (it runs only in the owner's login session, where the keychain and the notification centre are); `StandardErrorPath <home>/logs/launchd-refresh.err` from the real `Paths` (so a non-default `$SIDELOAD_HOME` is honoured); `StandardOutPath /dev/null` (the command's one JSON object is not kept; the log is); `EnvironmentVariables {SIDELOAD_HOME}` only when the home is not `<user home>/.sideload`; no `KeepAlive`, so a failed run is not retried before the next interval. Keys are written sorted, with tab indentation, as `plutil` would; every string is XML-escaped (`&`, `<`, `>`, quotes), so a binary path with those characters round-trips.
- **The owner's commands (`install`).** (1) `mkdir -p` of `~/Library/LaunchAgents` and the logs folder (launchd makes neither); (2) `cat > <path> <<'SIDELOAD_PLIST_END'` with the plist (a quoted here-document, so the shell expands nothing in it); (3) `/usr/bin/plutil -lint <path>`; (4) `launchctl bootstrap gui/$(id -u) <path>`; (5) `launchctl kickstart -k gui/$(id -u)/<label>` (the first run at once, since `RunAtLoad` is false). `stop`: `touch <home>/refresh.disabled` (every run skips with `KILL_SWITCH`; `rm` resumes; the agent stays loaded) and `launchctl bootout gui/$(id -u)/<label>` (unloads it). Paths are single-quoted only when they hold anything but letters, digits and `_@%+=:,./-`.
- **Not masked.** `Output.render` masks `/Users/<name>` to `/Users/<user>` in every envelope, which would make this plist and these paths useless. `Envelope.keepsUserPaths` (false by default; only `printAgent` sets it) skips that one pattern for this output; UDIDs, identity names, emails, tokens and private-key blocks are still masked. The output holds the owner's own home path and nothing secret.
- **Never run by an agent: the commands it prints.** `launchctl`, `device auto-refresh` and writing into `~/Library/LaunchAgents` are the owner's (Ask the owner first).
- **Tests.** `RefreshAgentTests`: the golden plist, `PropertyListSerialization` parse with exactly the planned keys (no `KeepAlive`), escaping of `&`, `<` and a space in the binary, `SIDELOAD_HOME` only for a non-default home, the printed commands, shell quoting, `USAGE` for a bad `--binary` and every option combination, no subprocess and no file (a fake runner and an empty temp directory), and that only this envelope keeps the user path. `MenuLoaderTests`: the local load turns the auto-renew wording on.

**Add app (menu, first install of a fetched app).** `refresh` never installs an app the device does not have, so the menu's "Add app…" (section 12) is the first-install chain: `fetch --app <a>` (stage 1, its own confirm), then, after the owner approves that exact version and file in the second confirm, `fetch --approve --version <v>`, `provision` (skipped when a stored profile has 6 days or more left), `sign` with `SignOptions.version` (skipped when `freeSigned` already holds this version, file and profile) and `install`. Each command takes `.op.lock` itself; the owner's click is every `--yes`. A new App ID is checked against the budget before the confirm opens (`FreeAppIdBudget.evaluate`), and the app's minimum OS against the device's before `provision` spends one. A run that stops halfway leaves approved only, a profile (App ID spent) or a signed build ("Signed · not installed", finished by Install), and the same Add app resumes. Run on a real device by the owner only; agents never click it.

**Update (menu, a newer version of an installed app).** The same chain over an app that is already installed (section 12, Update): `fetch --app <a>` (confirm 1), then after the owner approves that exact version and file, `fetch --approve --version <v>`, `provision` unless the stored profile has 6 days or more left (under 6 days it also renews the profile, and confirm 2 says so; the App ID is reused, and the budget is checked only if a new one would be registered), `sign` with `SignOptions.version` and `install` over the installed app (its data is kept, no slot is used). It is offered only for a recorded install (`installs[]`) whose approved source lists a strictly newer, parseable version (`updates.json`, `VersionOrder`). A run that stops halfway leaves approved only, a profile, or a signed build that the row's Install update finishes; `refresh` and Renew keep the installed version, so they never finish an update on their own. Run on a real device by the owner only; agents never click it.

1. Note atvloadly's Stremio expiry and last refresh; screenshot Remote App and Devices; do not update tvOS.
2. Pair in Xcode > Devices and Simulators; keep both hosts listed.
3. Stop atvloadly's Stremio refresh in its UI; keep the VM, the pair record and the app.
4. `device save --alias appletv --platform tvos --yes`; set `freeSlotsReserved: 1`.
5. provision, sign and install `io.github.dividedby.free.stremio` side by side with atvloadly's copy (nothing is overwritten); sign in to Stremio to sync addons.

2. **Built.** Team policy: `Config.swift`, `KeychainClient.swift`, `Guard.run(context:)`, `CertCheck` (free selection; doctor info row with fp8 and expiry). Guard(.free) codes: `BUNDLE_ID_NOT_ALLOWED` (checked first, before any subprocess), `GUARD_FAILED` (codesign or profile unreadable, bundle unlistable), `WRONG_TEAM` (codesign or profile team is not the free team, the paid team included), `PROFILE_INVALID` (`now >= ExpirationDate` or no expiry date, with the clock passed in `FreeSigning.now`; or `application-identifier` is not exactly `6ZU5Z6ZKK7.<id>`), `DEVICE_NOT_IN_PROFILE`, `PROFILE_CERT_MISMATCH` (pinned certificate not in `DeveloperCertificates`), then `GUARD_FAILED` unless `codesign -d --extract-certificates` (into a 0700 scratch directory under `FreeSigning.scratchRoot`, removed on every path) yields a leaf whose SHA-1 equals the pin, so the app is proven to be signed with it, not just listed in the profile, `EXTENSION_REMAINS` (any `*.appex`, case-insensitive; a symlink named `*.appex` counts), in that order. The app's own identity must also match the caller's bundle ID, else `GUARD_FAILED`: `codesign` `Identifier=` (right after the team check), then `Info.plist` `CFBundleIdentifier` and, when `codesign -d --entitlements` prints a readable plist, its `application-identifier` (just before the `.appex` scan). The identity snapshot covers every free-OU identity, valid or not, by SHA-1. Tests: paid paths still `FREE_TEAM_SELECTED`; `Guard(.free)` rejects the paid team, a wrong app-id, a non-allowlisted ID, a missing pinned cert.

A wrong JSON type is still `CONFIG_INVALID` for the whole file. Written only when set; `platform` stays `ios` or `tvos` as `device save` records it (an iPad is `ios` in devicectl; a separate `ipados` value is not recorded).
   - **Commands.** `device auto-refresh --alias a --on|--off --yes` and `device slots --alias a --reserved 0-3 --yes`: owner-only, check usage then the alias (`DEVICE_NOT_SAVED`) then `--yes` (`CONFIRM_REQUIRED`), write through `ConfigStore.update`, print one object, run no subprocess.

The alias must be saved, still have ledger records (the old alias's records otherwise stay, and a new device saved under the same alias would inherit them), or still have a folder under `profiles/free/*/<alias>` or `builds/signed/*/<alias>` (what a run that died after the ledger write leaves, so a rerun is accepted). If `bundleIdPrefix` is missing or invalid and backups exist for the alias, the check cannot run and it refuses with `restore_unknown` instead of skipping. The refusals come before `CONFIRM_REQUIRED`, which previews the counts. With `--yes` it takes `.op.lock`, rechecks the slots inside the ledger write, drops the alias's records, deletes its folders, then removes the config entry (`DEVICE_REMOVE_INCOMPLETE` if a folder cannot be deleted; a rerun finishes). Installs still recorded present are forgotten, not uninstalled (`INSTALLS_LEFT_ON_DEVICE`): the usual reason to retire a device is that it is gone. Backups under `backups/<alias>/` are kept and only counted (`BACKUPS_KEPT`). Known gap: aliases that differ only in case are not handled. `device save`'s `ALIAS_EXISTS` fix now names `device remove`.

**Risks**
- **Certificates.** `xcodebuild` may create a free certificate, or fail at the certificate limit; a revocation by atvloadly or Xcode breaks the lab. Mitigations: the pinned fingerprint and identity diff (hard stop and suspend) and retiring atvloadly (done 2026-10-30). Revocation is detected only after the fact, through trust evaluation.
- **No renewal (S3)** would make refresh a no-op; `PROFILE_NOT_RENEWED` turns that into suspension, not churn.
- **3-app limit:** the iPhone is full after Apollo; auto mode never adds an app.
- **atvloadly collision:** avoided by the distinct ID and the allowlist; the overlap used 2 TV slots until atvloadly's copy was removed on 2026-10-24.
- **Auto loop:** bounded by the caps (at most 4 installs per device per day), backoff, suspend, the shared lock, the kill switch and launchd's single instance.
- **Xcode account session expiry:** suspend and notify; never a prompt or a password.
- **Dropped app group** may break Apollo settings (owner decision).
